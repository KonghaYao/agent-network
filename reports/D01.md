## 最终行为与变更

### 1. 权威模型与迁移

- `migrations/0017_task_workflow.sql` 新增冻结契约要求的 `tasks`、`task_assignments`、`task_transfers`、`task_submissions`、`task_reviews`、`task_deliveries`，并新增两张实现补充表：
  - `task_cards`：保存任务卡片对应的真实 `message_id`。冻结的 `tasks` 没有 `card_message_id` 列，而 `deliveries.message_id NOT NULL` 要求指派投递必须引用真实消息，因此用一对一映射表表达。
  - `task_attachments`：只保存受控附件引用（`file_id` + 展示标签），不复制文件内容、不授予文件读取权限；文件读取仍走房间文件/成果自己的授权入口。
- 唯一性：`idx_tasks_source_message` 保证一条来源消息至多生成一个任务；`idx_task_assignments_current` 保证每个任务最多一个 `offered/active` assignment；`idx_task_deliveries_assignment_kind` 保证同一 assignment 的同类 delivery 只有一条。
- 旧 `room_tasks` 只读保留并一次性回填：`pending → unassigned`、`claimed → in_progress` 且生成 `asg_legacy_<task_id>` 的 v1 active assignment、`done → legacy_completed`、`failed → failed`；标题取 `substr(description, 1, 120)`，验收人为创建者。旧 `task_*` ID 原样迁入，新任务使用 `tsk_`，不冲突。
- 迁移编号 `0017` 位于既有 `0018..0028` 之前，按迁移器顺序执行；未修改任何已合入迁移。

### 2. 创建：消息转任务与任务卡片

- `network_task_create` 接收 `room_id`、`title`、`description`、`acceptance_criteria`、`source_message_id`、`assignee_actor_id`、`reviewer_actor_id`、`due_at`、`attachments`、`request_id`。
- `title` 1–120 字用于列表；长目标与验收条件分别写入 `description`（≤64 KiB）与 `acceptance_criteria`（≤16 KiB），不再塞进旧的 120 字短文本。附件最多 20 个，只存引用。期限上限 10 年。
- `source_message_id` 必须是同一房间内当前调用者可见的消息。创建与卡片消息写入、事件、outbox 在同一 `db.batch()` 内完成。
- 事务内写一条“【任务卡】”真实消息，正文包含短标题、状态与详情入口；`task_cards` 记录其 `message_id`，聊天历史、房间任务面板与“我的任务”都指向同一 `task_id`。转发/引用卡片只复制消息，不复制任务或授权；卡片正文、转发、引用与代码块不会被解析成新的 `invoke`。
- 同一 `request_id` 重放返回原结果；同一 `source_message_id` 的并发/重复创建通过 `convergeSourceTask` 收敛：参数一致返回同一任务，参数不同返回 `CONFLICT`。不会生成第二个任务、第二张卡片或第二次唤醒。

### 3. 指派、公开领取与取消

- 指派（`network_task_offer`）只作用于 `unassigned` 任务，候选负责人必须是具有该任务访问资格的有效成员；验收人不能与负责人相同，执行者不能是唯一验收人；`contact_blocks` 在指派、领取路径上校验。
- 指定 Agent：生成且只生成一条 `deliveries` 记录，绑定 `task_id` 与 `assignment_version`，`pending_count + 1`，并写 inbox `delivery_created` 唤醒。指派只形成 `offered` offer，不等于接单，任务不会自动进入 `in_progress`。
- 指定人类：写持久 inbox `task_offered` 事件，`pendingDelta 0`，不创建 `deliveries` 行，不伪造投递。
- 公开任务（`unassigned`）：不创建 delivery、不改变 `pending_count`、不向所有 Agent 发 `action_required`；房间任务事件只通知 active human。
- `network_task_claim`：human 或 Agent 的有效成员都可调用，原子地把 `unassigned → in_progress` 并生成 v1 assignment；不创建 delivery、不改变 `pending_count`。并发领取恰好一个成功，失败方返回 `CLAIM_CONFLICT`（不是通用状态错误），并可继续读取真实负责人。
- `network_task_cancel`：状态转为 `cancelled`，撤销 current assignment，关闭 pending delivery 并相应减少 `pending_count`；幂等重放不会重复扣减。
- `network_task_get` 返回 `can_accept` / `can_decline` 等只读提示；接受/拒绝、进展、阻塞、转派、提交与验收属于 D02/D03/D07/D08，本任务未实现，也不伪造状态。

### 4. 读取、可见性与通知边界

- 所有读取要求调用者仍是 active 成员，并受群历史边界约束。非成员、边界外与不存在统一返回 `NOT_FOUND`（`task_get` 不泄露 task_id 是否存在）；房间列表对非成员返回 `NOT_MEMBER`。
- `network_task_list` 支持 `room_id` 与 `scope: 'mine'`；“我的任务”覆盖我创建、我负责、我验收、待我接手的任务。`network_task_summary` 按房间返回 `pending/claimed/done/failed/total`，其中 `pending` 是公开未领取，`claimed` 只统计当前身份负责的进行中任务；供登录、唤醒与侧栏 badge 使用，只读且不改变 `pending_count`、房间 head 与未读。
- 任务房间事件映射为 `source='task.updated'`、`kind='task'`、`informational`，只发给 active human；不写 inbox、不推进 `rooms.head_seq`、不产生未读。人类接手请求使用 inbox `task_offered`，标记 `action_required`；取消为 `informational`。
- 事件项携带稳定定位字段 `task_id`、`assignment_id`、`status`，网页据此刷新任务视图。
- `src/domain/agent-management.ts` 的 `pending_work` 改读新 `tasks`：自己负责的 `in_progress/blocked/submitted` 计入 `claimed`，待自己接手的 `offered` assignment 计入 `pending`；停用 Agent 不再依赖旧 `room_tasks` 状态。
- `src/domain/rooms.ts` 的策略影响统计改为统计新 `tasks` 中早于成员加入时间的隐藏任务。

### 5. 网页入口

- 新增 `src/web/chat-tasks-script.ts`：聊天内任务卡片、房间任务面板、头部 `任务 done/total`、侧栏 badge、任务概览浮层、“我的任务”弹窗、从消息创建任务的弹窗与任务详情弹窗。
- 任务卡片只显示状态、负责人与详情入口；详情按 `network_task_get` 渲染业务权威来源（`native` / `external`）。创建弹窗可携带当前消息作为 `source_message_id` 并给出提示。
- 任务事件到达时刷新当前视图并提示；不轮询。侧栏 badge 每次会话列表加载只调用一次 `network_task_summary`。
- 新增样式集中在 `src/web/chat-styles.ts`，DOM 标记在 `src/web/chat-panels.ts`，消息卡片插槽在 `src/web/chat-render-script.ts` 与 `src/web/chat-stream-script.ts`。

### 6. 工具面、文档与脚本

- 任务工具固定为 7 个：`network_task_summary`、`network_task_list`、`network_task_get`、`network_task_create`、`network_task_offer`、`network_task_claim`、`network_task_cancel`。
- 退休旧 8 个任务板工具：`network_task_list_get`、`network_task_add`、`network_task_complete`、`network_task_fail`、`network_task_update`、`network_task_delete`（以及旧的领取语义），相关协议/网页/身份/群历史脚本与文档同步更新。
- `network_login` 返回只读 `task_summary`；`src/mcp/skill.ts`、`public/skills/agent_tasks.sh`、`public/skills/agent-network-skills.md` 增加任务创建、指派、领取、取消与“不要轮询”的说明；`README.md`、`CLAUDE.md`、`docs/code-index.md` 同步。
- 旧 `tests`/协议断言中的任务示例改为新工具与新状态（`claimed → in_progress`），`feedback-unit` 的旧库升级断言加入 `0017` 与三张新表。

## 契约、权限与数据变化

- **工具面**：新增 7 个任务工具与对应 schema/输出；`network_login` 增加只读 `task_summary`。旧 8 个任务板工具退休，旧客户端需同步升级。工具与事件形状遵循 `02-CONTRACTS.md` 已冻结的 `webots-p0-v1`，未改动已合入契约。
- **事件/订阅**：房间任务事件新增 `source='task.updated'`、`kind='task'` 与 `task_id`/`assignment_id`/`status` 字段；只发给 active human，informational，不写 inbox、不推进 head、不产生未读。inbox 新增 `task_offered`/`task_cancelled` 映射；`task_offered` 为 `action_required`。
- **持久状态**：新增 8 张表（6 张契约表 + `task_cards`/`task_attachments`），旧 `room_tasks` 只读保留并回填。迁移是纯增量，无破坏性列修改。
- **权限**：读取要求 active 成员 + 历史边界；`task_get` 对非成员/边界外/不存在统一 `NOT_FOUND`，房间列表 `NOT_MEMBER`。指派、领取校验成员资格、验收人独立性、`contact_blocks`；任务 owner 仍须通过同一房间授权，不因任务身份获得额外房间权限。
- **网页**：新增任务卡片/面板/弹窗与样式；不改变既有消息、文件、监控接口。任务卡片不解析 `invoke`，转发/引用不复制任务或授权。
- **文档/脚本**：`README.md`、`CLAUDE.md`、`docs/code-index.md`、技能正文、`public/skills/agent_tasks.sh` 与协议/网页/身份/群历史/反馈脚本同步更新。

## 问题与限制

1. **全量 `test:acceptance` 未绿（基线问题）**：`scripts/acceptance.ts:1034` 的离线断言与 `reports/BASELINE.md` §3.7 一致，30 s 等待短于在线活动 TTL；本次未修改 presence 语义。D01 专项验收与其余套件均已通过。需要在集成环境修复该基线用例或调整等待策略后，才能取得全量端到端绿。
2. **成果（artifact）尚未接入新任务**：`src/domain/artifacts.ts:206` 仍通过 `getRoomTask` 校验 `room_tasks`，`scripts/verify-m07.ts` 也仍写入/断言旧表，因此 `tsk_` 任务暂不能提交成果。属于 D07/D08 与 M07 的集成范围。
3. **文件引用回收未覆盖任务附件**：`src/maintenance.ts:31` 的引用回收只检查 `room_tasks`，未检查 `tasks`/`task_attachments`；若新任务附件引用文件，理论上可能被提前回收。建议在 D07/D08 接入时一并修正。
4. **生命周期子集**：接受/拒绝 offer（D02）、进展/阻塞/转派（D03）、提交与验收（D07/D08）未实现；`can_accept`/`can_decline` 只读展示；`task_transfers`/`task_submissions`/`task_reviews` 表已建但未使用；offer 过期没有清扫器，只保留 `offer_expires_at` 数据。
5. **列表分页**：`network_task_list` 返回 `next_cursor: null`、`has_more: false`，尚未分页；`LIMITS` 已提供默认/上限，后续任务量增大时需补游标。
6. **通知范围**：人类接手请求走持久 inbox；没有额外的浏览器推送通道。网页依赖订阅通知与打开视图时刷新，明确不轮询。
