## 最终行为与变更

### 1. 双边确认与唯一 pending

- `network_agent_transfer_propose { request_id, actor_id, to_manager_id, note?, expires_in_ms? }` 只允许该 Agent 的 active manager（委托人与 Agent 自己返回 `PERMISSION_DENIED`）。接任者必须是已注册、有有效凭据、未停用/归档的 human，不能是当前管理者或 Agent 自己；同一 Agent 只允许一条 pending，默认 `LIMITS.agentTransferTtlMs = 24h`，测试可缩短到 1s。实现见 `src/domain/agent-transfers.ts:46`，表约束仍是 `idx_agent_transfers_pending`。
- `network_agent_transfer_respond { transfer_id, decision: accept | reject }` 只允许 `to_manager` 本人；`network_agent_transfer_cancel` 只允许发起人；错误身份统一按 `NOT_FOUND` 处理，避免泄露他人的交接。`network_agent_transfer_get` / `_list` 只对发起人、接任者、目标 Agent 本人和该 Agent 的有效 `manage_agent` 受托人可见。
- 拒绝、取消、过期只关闭提议：不修改 `agent_managements`、不撤销委托、不轮换凭据、不改任务。过期由 `expireAgentTransfers` 在读/发起/响应前收敛，并写 `management_transfer_expired` + `agent_transfer_expired` 审计别名与双方 human inbox 事件（`src/domain/agent-transfer-store.ts:341`）。
- 提议通知写入接任者个人 inbox：事件、outbox 与 `inbox_head_seq` 同一事务提交，`pending_count` 增量固定为 0；不创建 delivery，也不唤醒 Agent。接任者可用 `network_sync { scope: "inbox" }` 补读。

### 2. 接受事务、凭据轮换与重放

接受在单个 `db.batch()` 内完成（`src/domain/agent-transfers.ts:225`）：

1. 校验提议仍 pending、未过期且 `to_manager` 是调用者；校验当前管理关系仍是 `from_manager` 且 `permission_version = from_permission_version`；校验接任者仍有 human 有效凭据。
2. `agent_managements` 切换 `manager_id`、`grant_source = 'transfer'`、`permission_version + 1`。
3. 撤销该 Agent 全部 active `agent_delegations`。
4. 撤销该 Agent 全部未撤销 `credentials`，插入一条新的 SHA-256 凭据；raw token 只在首次响应出现。
5. 复用 D04 的 `revokeTaskEligibilityStatements`，以 `blocked_reason = management_transferred`、`reason = management_transferred` 处理该 Agent 在所有房间的未结束任务：撤销 active/offered assignment、关闭 assignment 的 pending/claimed 任务投递、取消 pending 任务交接；`in_progress` / `blocked` 进入 blocked，未接受的 `offered` 回到 `unassigned`。绝不自动 accepted/completed。
6. 写 `management_transfer_accepted`、`agent_transfer_accepted`、`management_transferred`、`credential_rotated` 审计与双方 human inbox；审计包含双方、`permission_version`、撤销委托/凭据数、blocked/unassigned 任务 ID、取消投递数与上下文快照。
7. 事务提交后由工具层 `revokeCredential`（逐个旧凭据）与 `closeActorStreams` 关闭旧运行连接；旧 token 立即 `CREDENTIAL_INVALID`。

`operations.result_json` 只保存非秘密结果：`token` / `mcp_url` 为 `null`。首次接受返回 `{ ...stored, token, mcp_url }`；同一 `request_id` 重放返回同一非秘密结果，不再轮换、不再关闭新连接。拒绝/取消/过期的结果同样不包含凭据。

拒绝/取消/过期不改管理权、不轮换凭据；`REQUEST_EXPIRED`、`CONFLICT`、`CLAIM_CONFLICT`、`VERSION_CONFLICT`、`PERMISSION_DENIED` 按事务提交顺序裁决。旧管理者在交接提交后调用改名、重发、停用、归档、读取管理等一律 `PERMISSION_DENIED`。

### 3. 任务状态机与重派

- 任务失权仍由 D04 的统一入口处理，没有第二套 blocked/assignment 状态机。`revokeTaskEligibilityStatements` 新增可选 `blockedReason` 与只读 `onTask` 回调（`src/domain/task-transfers.ts:373`），默认行为对停用/退群等调用方保持不变。
- `in_progress` / `blocked` 任务进入 blocked 并记录 `management_transferred`；已 offered 但未接受的任务回到 unassigned。这样既满足“交接不自动结单”，也与 D04 的“未接受 offer 不冒充执行中”一致。
- 交接后的 blocked 任务没有 owner/assignment；`network_task_offer` 在任务为 blocked 且没有 owner/assignment 时允许有权派发者显式重派（`src/domain/tasks.ts:1993`），重派时清空 `blocked_reason` 并生成新 assignment。已有 owner 的 blocked 任务仍不能绕过原负责人。
- 旧 token 失效且旧 assignment 已 revoked；用新 token 携带旧 assignment 提交仍返回 `ASSIGNMENT_STALE`/`PERMISSION_DENIED`/`CONFLICT`（T03 实测）。任务不会因管理权交接自动 accepted/completed。

### 4. 读取面与隐私边界

- `network_agent_management_get` 保持原有字段并追加：`rooms`（active 群关系）、`delegations`（active 委托）、`pending_transfer`、`in_flight_deliveries`（pending/claimed 明细，仅定位信息）、`audit_summary`、`can_transfer`；`my_role` 增加 `successor`。接任者确认前可读管理范围与在途工作，但 `can_manage = false`（`src/domain/agent-management.ts:229`，读取实现见 `src/domain/agent-transfer-reads.ts`）。
- 交接不复制原管理者的私聊、联系人、群成员身份或外部平台授权；不把新管理者加入任何房间，不创建联系人、不写 `room_members`、不碰外部 Issue/仓库授权。T04 实测新管理者读取原管理者私聊返回 `PERMISSION_DENIED`/`NOT_MEMBER`，联系人列表不包含原管理者联系人，管理摘要不含私聊正文。
- 审计摘要只返回白名单字段，不含 token、凭据摘要或消息正文。

### 5. Web

- direct Agent 右键菜单新增“交接管理权”（群聊与人类会话隐藏）；面板在 `src/web/chat-transfer-script.ts`，DOM 在 `src/web/chat-panels.ts`。
- 当前管理者可搜索好友、选择有效 human、发起/取消；接任者可接受/拒绝。面板展示 pending 状态、在途群关系/任务/投递摘要与大体积在途工作清单。
- 接受成功后一次性显示新 MCP URL，提示“新 token 只显示一次；只通过受控渠道配置，勿发群、截图或写日志”，并写入接受方本机 Agents 注册表；关闭面板立即从 DOM 清除 token。
- 保持现有 DOM id/class 与移动端单栏；新增脚本 403 行，`chat-room-menu-script.ts` 783 行，未引入外部二维码/凭据服务。

## 问题与限制

1. **不自动转移群/私聊成员资格**：交接只改 `agent_managements`，新管理者不会自动加入原管理者的私聊或 Agent 所在群。要显式重派群内任务，新管理者必须先由群 owner/admin 加入房间并获得派发权限（本专项 T03 用群 owner 接任者覆盖）。这与任务要求“不自动转移私聊”一致，但意味着“新管理者可重派”以房间可见性为前提。
2. **offered 任务回 unassigned，而非 blocked**：为兼容 D04“未接受 offer 不冒充执行中”，只有已接受/进行中/已 blocked 的任务记录 `management_transferred`。若验收要求“所有未结束任务一律 blocked”，需要 D04 一起调整；本次选择最小兼容实现。
3. **旧执行进程未被证明停止**：交接撤销凭据与 assignment，不声称外部进程已杀死；外部副作用仍按 D08 的 unknown/对账处理。旧执行者若持有已下载材料或本地 token 副本，服务端只能拒绝后续请求。
4. **审计计数为事务前快照**：`revoked_delegations`、`revoked_credentials`、blocked/unassigned 任务清单在事务提交前读取；并发新增委托可能被事务撤销但未计入数字。任务 ID 清单来自统一失权入口的实际匹配集合，未匹配的任务不会出现在结果中。
5. **事件命名双写**：为兼容冻结契约同时写 `agent_transfer_*` 审计别名，审计摘要只展示 `management_transfer_*`/`management_transferred`/`credential_rotated`，避免重复。集成时若要统一事件名，可删除别名，不影响业务状态。
6. **外部平台授权不继承**：仓库/Issue/API key 授权不在本任务范围，代码没有复制任何外部绑定；T04 通过联系人、私聊与 `management_get` 审计验证没有横向扩散，但没有真实外部发布系统可联调（Q03 依赖）。
7. **Web 新 token 只在本机注册表**：接受方浏览器把新 MCP URL 写入自己的 `localStorage` 注册表；这是本机受控渠道，不是服务端代管。清除站点数据或换浏览器后需由新管理者重新配置，不得通过群消息传递。
8. **未做压力测试**：6 轮并发覆盖两种提交顺序，未跑 100 次固定种子竞争；全局并发矩阵由集成验证补充。
