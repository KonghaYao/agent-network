## 最终行为与变更

### 1. 服务端发送对账（复用 + 新增）

- `network_message_send` 原有的 `request_id` 幂等与 `client_message_id` 唯一约束保持不变：同一 `request_id` 重放返回同一结果；同一 `client_message_id` 以新 `request_id` 重试时，由 `messages` 唯一键冲突恢复既有消息与 delivery 集合；正文或房间不同返回 `IDEMPOTENCY_CONFLICT` 且 `details.message_id` 指向既有消息。正文、delivery、事件与 outbox 仍在同一 `db.batch()` 中提交。
- 新增只读工具 `network_message_send_status { client_message_ids: string[1..20] }`（`src/domain/messages.ts`、`src/contracts/schemas.ts`、`src/mcp/outputs.ts`、`src/mcp/tools.ts`）。只按当前发送者自己的 `client_message_id` 返回 `found`、`message_id`、`room_id`、`created_seq`、`delivery_ids`、`body_bytes`、`created_at`；不返回正文、preview 或成员信息。未找到时 `found: false` 且其余字段为 `null`/`[]`。
- 对账查询使用 `messages(sender_id, client_message_id)` 唯一索引；批量查询 delivery 后按 `delivery_id` 排序，输入去重且保持首次出现顺序。工具标记 `readOnlyHint: true`，不写 operations/events/outbox，不推进 `rooms.head_seq`。
- 撤权后：新的发送和幂等重放仍先做成员校验，返回 `NOT_MEMBER`；`network_message_read` / `network_history_list` 继续拒绝。发送者仍可调用 `network_message_send_status` 确认既有消息是否提交，但拿不到正文，避免响应丢失后重复发送。

### 2. 网页持久发送意图（新增）

- 新增 `src/web/chat-outbox-script.ts`，按 actor 隔离存放于 `localStorage['agent-network-outbox:v1:<actor_id>']`：保存 `client_message_id`、`request_id`、`room_id`、正文、`invoke`、状态、尝试次数与时间。上限 `LIMITS.webOutboxMax = 50`、未确认 TTL `webOutboxTtlMs = 24h`、已提交提示保留 `webOutboxCommittedMs = 60s`。
- 状态机 `sending → committed | failed`；`failed` 区分可重试（无 code 的传输/超时、`RATE_LIMITED`、`CONFLICT`、`DRIVE_UNAVAILABLE`）与不可重试。状态行只渲染在当前房间时间线末尾，样式为 `.msg-outbox`，不进入 `currentItems`、排序、未读或 `head_seq`。
- `src/web/chat-script.ts` 的提交路径改为：同房间/同正文/同目标的失败意图复用原 `client_message_id` 与 `request_id`，重试前先对账；否则新建意图。`sendButton.disabled` 同时作为并发提交闸门，避免连按回车生成两条意图。
- 响应丢失时（异常或 15 秒超时）先调用 `network_message_send_status` 对账：`found: true` 则标记已提交并补拉时间线，不重发；确认未找到才标记可重试失败。页面加载、统一流重连与 `online` 事件触发单飞对账（不轮询）。
- 时间线渲染时（`src/web/chat-render-script.ts`）按服务端 `message_id` 清理已提交意图，再追加当前房间的状态行；切群、刷新、迟到响应只更新对应房间，不覆盖当前草稿或状态。退出登录（`src/web/chat-logout-script.ts`）清除全部本地意图。
- 草稿与附件仍按房间保存；已提交后只有当前房间且输入框仍是该意图正文时才清空，后台房间的迟到成功不清空新房间输入。

### 3. 恢复与去重（复用，未改语义）

- 服务端继续分配唯一、单调的 `created_seq`；`network_sync` 按事件 `seq` 返回，`network_history_list` 按 `created_seq` 返回。网页 `mergeTimelineItems` 以 `message_id`（presence 以 `presence_event_id`）为稳定键去重，按时间与提交序号排序；`fetchRoomUpdate` 从 `timeline_resume_cursor` 补到最新页水位，游标不前进时停止。
- outbox 只负责“这条发送意图是否已提交”，不改变消息存在性：通知丢失、重复或乱序时仍以 SQLite 的 sync/history 读取为准。

### 4. 文档与工具面

- `src/mcp/server.ts` 的 instructions、`src/mcp/skill.ts` 与 `public/skills/agent-network-skills.md` 补充对账与补读纪律；`README.md` 工具数 81 → 82（关闭 Drive 时 77），协议验收 745 → 747。
- `scripts/verify-protocol.ts` 增加工具清单与只读/输出 schema 断言；`scripts/acceptance.ts` 接入 M02 端到端片段；`scripts/verify-web.ts` 增加 M02 界面片段。

## 契约、权限与数据变化

- 共享工具面新增只读 `network_message_send_status`；输入 `{ client_message_ids: string[] }`（1–20），输出 `{ items: [{ client_message_id, found, message_id, room_id, created_seq, delivery_ids, body_bytes, created_at }] }`。不新增错误码。
- 新增 `LIMITS.messageSendStatusMax = 20`、`webOutboxMax = 50`、`webOutboxTtlMs = 24h`、`webOutboxCommittedMs = 60s`；阈值只在 `src/contracts/limits.ts` 维护。
- **无迁移**：`migrations/0001_initial.sql` 已含 `UNIQUE (sender_id, client_message_id)`，本次对账直接使用该索引；未修改任何既有迁移，未新增临时表或列。
- 时间线、`rooms.head_seq`、未读水位与 `pending_count`：对账工具只读；网页 outbox 是浏览器本地状态，不写服务端事件/outbox；重试复用同一消息，因此 head 只推进一次。既有同步/历史/已读语义未改变。
- 撤权边界：发送与正文读取继续按“当前身份 + 有效成员”判断；对账工具只返回发送者自己的消息定位信息，不返回正文内容。

## 问题与限制

1. **对账指纹是正文长度而非正文摘要**：`network_message_send_status` 有意不返回正文/preview，网页以 `room_id + body_bytes` 判断本地意图是否对应已提交消息。服务端发送时仍做精确正文比较，客户端修改正文会新建意图，因此不会产生第二条消息；只有“同一 `client_message_id` 被外部复用为同字节长度的不同正文”这种违反客户端协议的场景才可能把旧意图误判为已提交。后续若需要更强保证，可在不改授权的前提下增加正文摘要字段并同步客户端与服务端。
2. **本地意图是浏览器本地状态**：清空 localStorage 会丢失未确认意图的正文与重试入口，但已提交消息仍可从 history 恢复；换设备不会看到另一台设备的失败意图。
3. **重试是显式操作**：失败意图不会自动重发；`online`/重连只触发对账，避免后台重复提交与轮询。
4. **T01 的响应丢失模拟**：服务端验收通过“同一业务请求重复提交”模拟响应丢失，网页验收在 HTTP 层真实丢弃响应后再重试；两者分别覆盖协议收敛与客户端对账路径。
5. **本地验收的 presence 环境**：`test:acceptance` 的既有 presence 用例要求服务端与测试进程同时使用短 `AGENT_PRESENCE_*`；未设置时会在“关闭最后一个连接后成员显示离线”等待超时（`reports/INTEGRATION.md` 已记录），属于运行配置而非本次代码回归。设置后 1219 项全部通过。
6. **对账工具允许撤权后定位**：这是为了响应丢失后不重复发送，且结果不含正文、preview 或成员信息；若后续产品要求撤权后完全不可见消息存在性，需要单独评审并调整 M02-T04 期望。
