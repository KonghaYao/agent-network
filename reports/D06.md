## 最终行为与变更

### 1. 提交资格与不可变版本

- `network_task_submit` 只接受当前任务负责人，且必须持有 `tasks.current_assignment_id` 对应的 active assignment、任务处于 `in_progress`。提交同时校验 `expected_revision`、可选 `assignment_id` / `assignment_version`：非负责人返回 `PERMISSION_DENIED`，旧执行资格返回 `ASSIGNMENT_STALE`，旧 revision 返回 `VERSION_CONFLICT`，任务状态不是 `in_progress` 返回 `CONFLICT`。
- `summary` 必填；材料、外链、验证证据与 `commit_sha` 至少提供一项，否则 `INVALID_ARGUMENT`。`commit_sha` 归一化为小写 7–64 位十六进制；非代码任务可省略，但必须提供其他可核对成果。
- 每次成功提交生成新的 `submission_id` 与 `version = max(现存版本) + 1`，状态 `pending`。同一任务只允许一个 `pending` 版本：`idx_task_submissions_pending` 与提交前显式检查共同返回 `CONFLICT`；同一 `request_id` 重放返回原提交快照，不新增版本。
- 材料只接受同一房间、元数据完整且仍可用的文件。服务端在事务内重新读取文件元数据并冻结 `name`、`mime_type`、`size`、`sha256`；客户端传入的校验值不参与判定。材料不可用、跨房间、已过期或字节已删除返回 `FILE_UNAVAILABLE`。
- 外链保存 `url`、可选 `title` / `version` / `digest` 与 `availability`；缺省为 `unverified`，`declared_reachable` 只是提交者声明。只接受 `http`/`https` 绝对 URL，拒绝 URL 内嵌凭据，同一版本内按规范化 URL 去重。服务端不抓取外链，可变 URL 不被当作固定字节证据，可达也不等于验收通过。
- 验证证据逐条保存，已知限制单独保存；输出包含 `assignment_id`、`assignment_version`、提交人、提交时间、审核信息与 `is_current`。`get` 按版本读取（省略版本返回最新），`list` 按版本倒序返回最多 `LIMITS.taskSubmissionListMax` 条并给出 `has_more`。

### 2. 原子提交与失败回滚

- `taskSubmit` 经 `runIdempotent` 在同一个 `db.batch()` 中写入：operations 结果、成员 guard、task revision guard、`status = 'in_progress'` guard、active assignment guard、房间配额 guard、材料保留语句、提交行、任务状态更新、assignment 结束、投递关闭、pending 交接取消与 `task_submitted` 事件。任一步失败整批回滚，operations 不落行，任务、assignment、文件引用与提交表均保持原状。
- 任务更新保留 `owner_actor_id` 作为显示与审计来源，`current_assignment_id` 仍指向本次提交的 assignment；任务转 `submitted` 且 `revision + 1`，该 assignment 转 `submitted` 并写 `ended_at`。
- 同一事务关闭该 assignment 仍 `pending` / `claimed` 的 `task_offer` / `task_reminder` delivery，并通过 inbox 事件递减 `pending_count`；取消该任务的 pending 交接（`invalidated_by: 'submit'`），避免已交付任务被迟到接任。
- 文件保留引用复用 `file_references(kind = 'task', ref_id = task_id)`：同一批内建立 active 引用，房间文件置 `retained`，Drive 文件置 `retained` 并清空 TTL。成功时文件保留、提交行与任务状态同批生效；失败时不留下空提交或半保留文件。
- 提交不创建聊天消息或 delivery，不增加 Agent `pending_count`，不推进 `rooms.head_seq`，不产生未读。`task_submitted` 只作为 room scope 事件与 `room:<id>` outbox 写入，由 stream 投影为 `task.updated` / `informational`，只扇出 active human，并携带 `submission_id` / `submission_version`。

### 3. 最小退回与重提

- D06 只提供契约 C07 中 review 的**最小退回**入口 `network_task_submission_return`，不提供 accept；完整验收授权由 D07 补齐，避免出现两套互相冲突的退回/验收入口。
- 退回只允许当前验收人 `tasks.reviewer_actor_id`，任务必须 `submitted`、目标提交必须 `pending` 且属于该任务，提交人不能验收或退回自己的成果；违反时返回 `PERMISSION_DENIED` / `CONFLICT` / `NOT_FOUND`。
- 退回在同一事务写入 `task_reviews(decision = 'return')`、提交置 `returned`、任务 `revision + 1` 回到 `in_progress`，并为原负责人生成 `assignment_version = max + 1` 的新 active assignment；原负责人已失权或停用时任务转 `blocked`、`blocked_reason = 'owner_lost_eligibility'`、清空负责人与 assignment，不伪造执行资格。
- 退回写 `task_returned` room 事件与 outbox，仍只通知 active human；不创建 delivery、不增加 `pending_count`、不推进 `head_seq`。同一 `request_id` 重放返回原结果；对新 `request_id` 重复退回同一版本返回 `CONFLICT`。
- 只有退回后原负责人才能重新提交，生成 v2；v1 以 `returned` 保留，材料、外链与证据快照不被 v2 覆盖。旧 v1 回执不能修改已进入 `pending` 的 v2；任务卡片、任务列表与 `task_get` 的 `current_submission` 统一指向当前版本。
- `task_get` / `task_list` 新增 `current_submission`、`can_submit`、`can_return`：`can_submit` 只在当前负责人持有 active assignment 且任务 `in_progress` 时为真，`can_return` 只对当前验收人且存在 `pending` 版本时为真。

### 4. 工具、事件与网页

- 新增 `network_task_submit`、`network_task_submission_get`、`network_task_submission_list`、`network_task_submission_return`；`submit` / `return` 为写工具，`submission_get` / `submission_list` 标记 `readOnlyHint`。任务工具合计 22 个，旧看板工具保持退役。
- `src/realtime/stream.ts` 把 `task_submitted` / `task_returned` 与既有任务事件统一投影为 `source: 'task.updated'`、`kind: 'task'`、`attention: 'informational'`，只发给 active human；`StreamItem` 增加 `submission_id` / `submission_version`。
- 网页在 `src/web/chat-task-submission-script.ts` 实现：任务详情显示当前版本徽标、提交时间与提交历史（状态、摘要、退回原因）；提交弹窗提供摘要、房间文件多选与材料标签、外链（URL/标题/版本/摘要）、实现提交 SHA、验证证据与已知限制；退回入口要求可行动原因。材料列表复用 `network_room_file_list`，提交后重新读取任务详情、任务概览与房间任务；失败保留表单并显示服务端错误。列表与任务卡片显示版本徽标。
- `src/mcp/skill.ts` 与 `public/skills/agent-network-skills.md` 同步提交/读取/退回语义、错误码与 human-only 事件；`README.md`、`docs/code-index.md` 记录 D06 入口。`scripts/verify-protocol.ts` 增加工具注册、输入/输出 schema、描述、只读提示与技能正文断言；`scripts/acceptance.ts` 注册 D06 专项。

## 契约、权限与数据变化

- **迁移**：新增 `migrations/0032_task_submission_sources.sql`，只给冻结表 `task_submissions` 追加 `links_json TEXT NOT NULL DEFAULT '[]'` 与 `commit_sha TEXT`，不重建表、不改变既有状态 CHECK。旧行读取为无外链、无提交 SHA；无需回填，也不会把旧提交误认为有 Git 证据。迁移注释包含用途、权威、约束与旧数据映射；追加列对旧代码透明，回退应用版本时旧代码会忽略未知列。
- **材料引用映射**：`migrations/0017_task_workflow.sql` 的 `file_references.kind` CHECK 不含 `submission`，且已发布迁移不可重建；D06 复用 `kind = 'task'`、`ref_id = task_id` 建立保留引用。语义是“任务成果材料”，与任务附件共享同一活跃引用计数；如未来需要区分提交版本，必须新增迁移，不能在本任务临时改表。
- **契约**：契约版本保持 `webots-p0-v1`。新增工具名落在契约的 `network_task_*` 与 review 语义内；D06 只实现契约 C07 的 return，accept 留给 D07，未新增第二个退回入口。没有共享契约偏离，也没有提交 `CHANGE_REQUEST.md`。
- **权限**：提交限当前负责人 + active assignment + `in_progress` + 任务可见（房间成员、历史边界内）；`submission_get` / `submission_list` 对任务可见成员开放，非成员/边界外/不存在统一 `NOT_FOUND`；退回只限 `reviewer_actor_id`，提交人不能审核自己的成果。
- **错误码**：沿用 `ASSIGNMENT_STALE`、`VERSION_CONFLICT`、`PERMISSION_DENIED`、`CONFLICT`、`NOT_FOUND`、`INVALID_ARGUMENT`、`IDEMPOTENCY_CONFLICT`、`TOKEN_NOT_REPLAYABLE`；新增业务失败 `FILE_UNAVAILABLE` 与 `QUOTA_EXCEEDED`，均映射到既有错误响应结构。
- **写入一致性**：全部写操作经 `runIdempotent`，同时校验成员、task revision、任务状态、active assignment 与配额；operations、提交、任务、assignment、delivery、交接与事件在同一 `db.batch()` 内全有或全无。
- **限制值**：提交摘要 16 KiB、材料 20 个、材料标签 1 KiB、外链 20 个（URL 2 KiB、标题 512 B、版本 256 B、摘要 256 B）、证据 20 条（每条 4 KiB）、已知限制 8 KiB、提交 SHA 64 B、退回原因 4 KiB、列表默认 50 / 上限 100。全部集中在 `src/contracts/limits.ts`。
- **客户端影响**：新增 4 个工具与 `current_submission` / `can_submit` / `can_return` 输出字段；网页新增提交弹窗、版本徽标、历史与退回入口。CLI `public/skills/agent_tasks.sh` 未扩展提交子命令，MCP 与网页入口已覆盖任务要求。

## 问题与限制

1. **D07 尚未上线**：D06 只有最小退回，没有 accept。任务提交后只能停在 `submitted` 等待 D07 的完整验收授权与通过路径；本任务不把退回实现成验收，也不把 delivery `completed` 映射为交付 `accepted`。
2. **未指定验收人的任务无法退回**：退回要求 `tasks.reviewer_actor_id` 等于调用者。创建任务时未指定验收人的任务需要先由 D07/创建者补齐验收人；当前不会自动选择验收人，避免扩大权限。
3. **提交读取对房间可见成员开放**：与 `task_get` 的可见性模型一致，不是仅提交者/验收人可见。若产品要求仅验收人可见材料清单，需要共享契约变更与新的授权规则，不能只改前端。
4. **外链只记录声明**：服务端不抓取、不缓存、不校验外链内容；`declared_reachable` 仅代表提交者声明。网页提交表单目前统一写入 `unverified`，未暴露“声明可访问”选项，避免把可选声明误当服务端验证。
5. **提交列表无游标**：`submission_list` 只支持 `limit`（默认 50、上限 100）与 `has_more`，不返回可继续翻页的游标；超过 100 个历史版本时，较早版本需按已知 `version` 用 `submission_get` 读取。正常任务的版本数远低于该上限。
6. **网页材料来源受限**：弹窗只从 `network_room_file_list` 读取已绑定房间文件（最多 100 个），不直接列出 Drive 私有草稿；未绑定文件需先在聊天/房间文件入口绑定。材料超出首屏 100 个时需先整理房间文件。
7. **`superseded` 状态未产生**：`task_submissions.status` 的冻结 CHECK 保留 `superseded`，D06 不写入该状态；D07 accepted 路径如需要版本替代语义，应在其迁移/实现中明确，而不能由 D06 猜测。
8. **网页入口无 D06 专项浏览器断言**：`test:web` 的 1939 项覆盖既有任务详情、列表、事件与凭据行为不回归，未新增提交弹窗、版本徽标与退回入口的端到端断言；界面入口已实现并通过 typecheck 与页面加载回归，独立验证时需手工核对提交、退回与 v2 展示。
9. **`commit_sha` 只做格式校验**：服务端不访问 Git 仓库，只能保证 7–64 位十六进制格式与归一化，不能证明该 SHA 存在或对应本次成果；验收人需自行核对。
10. **全量验收未执行**：按指令只跑 D06 专项、协议与网页验收；集成阶段需在集成 SHA 上重跑必需门禁，并补做 D06 与 D04/D07 的交叉路径。
