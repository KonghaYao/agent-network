## 最终行为与变更

### 1. 权威模型与凭据分离

- 新增 `agent_managements`（每个 Agent 至多一条 `active`，部分唯一索引）、`agent_claims`（一次性 `claim_code_hash`、尝试上限、15 分钟 TTL）、`agent_delegations`（`scopes_json` + 30 天默认 TTL）、`agent_management_transfers`、`devices`、`device_pairings`，并给 `actors` 增加 `disabled_at/disabled_by/disabled_reason`、给 `credentials` 增加 `last_used_at/revoked_by/label`。见 `migrations/0012_identity_management_devices.sql`。
- 管理权唯一来源是 SQLite 的 `agent_managements`。浏览器 `localStorage['agent-network-agents-v1']` 只作为缓存，`owner_actor_id` 不参与任何授权判断。
- 人类、Agent、管理者、设备凭据分开：管理动作只接受 `kind = human` 的调用者；Agent 自己的凭据只能维护自身资料、发起认领或取消自己的认领，不能管理自己或其他 Agent。

### 2. 创建与双端认领

- `network_agent_create { request_id, name }`：当前 human 凭据在同一 `db.batch()` 内原子写入 Agent actor、`agent_managements`（`grant_source = 'created'`、`permission_version = 1`）与初始 credential；raw token 只在首次响应出现，不写 `operations.result_json`，同一 `request_id` 重放返回 `TOKEN_NOT_REPLAYABLE`。
- 旧式 `network_register { kind: 'agent' }` 继续可用，但产生 `unclaimed` Agent，不自动绑定任何管理者。`network_agent_claim_start` 只允许 Agent 自身调用并返回一次性 code（服务端只存 SHA-256）；`network_agent_claim_confirm` 由 human 在另一端完成绑定（`grant_source = 'claim'`）；`network_agent_claim_cancel` 由发起 Agent 取消。错误 code 累计尝试次数，达到 `LIMITS.agentClaimMaxAttempts` 后认领被拒绝；过期按 `REQUEST_EXPIRED` 处理。
- 已有 active manager 的 Agent 再次发起认领返回 `CLAIM_CONFLICT`；不认识 actor_id、昵称、群主或 localStorage 的路径都不能自动认领。

### 3. 管理授权、委托与权限版本

- `src/domain/agent-access.ts` 统一实现 `managementAccess`、`requireManageAgent`、`managementPermissionGuard`、`managementVersionGuard`、`requireAgentTarget`。授权判定：active manager，或 active 且未过期、含 `manage_agent` scope 的 delegation。
- `network_agent_rename`、`network_agent_archive`、`network_agent_unarchive`、`network_agent_reissue_token` 从“任意已注册 principal 可操作”改为管理者/委托授权；预检与事务内 guard 双重执行，事务内重读授权，撤销委托与操作并发时按提交顺序裁决。
- `network_agent_rename` 与 `network_agent_reissue_token` 支持可选 `expected_permission_version`；不匹配返回 `VERSION_CONFLICT`。`network_agent_disable`、`network_agent_enable`、`network_agent_delegate_grant/revoke`、`network_agent_management_get`、`network_agents_managed_list` 一并加入工具面。
- 非秘密结果（归档/取消归档/确认认领/取消认领/撤销委托）先按 `request_id` 解析重放，保留 `IDEMPOTENCY_CONFLICT` 语义；一次性秘密（token、claim code）重放返回 `TOKEN_NOT_REPLAYABLE`，不重新暴露失权秘密。

### 4. 归档与停用正交

- 归档只写 `archived_at/archived_by`，不参与认证、投递、任务或凭据判断；归档后的 Agent 仍可聊天与调用工具。
- 停用在同一事务内：写 `disabled_at/by/reason`；撤销该 Agent 的 active delegations；递增 `agent_managements.permission_version`；取消 `pending` 与 `claimed` 投递；返回 `stopped` 待处理视图。停用不把任务静默标为完成。
- `authenticate()` 对 `kind = 'agent' && disabled_at !== null` 返回 `ACTOR_DISABLED`；消息 guard 增加 `guard_actor_disabled`，新 invoke 投递被拒绝。启用恢复凭据可用性，但不恢复已取消投递或已撤销委托。
- `NotificationHub.closeActorStreams(actorId)` 在重发 token 与停用时关闭旧连接的 stream；MCP Events dispatcher 以 `credentialState` 同时识别凭据撤销与 actor 停用，并暂停对应订阅。

### 5. 事件、审计与网页

- 管理事件写入 `events`：`agent_management_bound`、`agent_claim_requested/confirmed`、`agent_delegation_granted/revoked`、`agent_disabled/enabled`、`credential_reissued`、`profile_updated`；只向管理者/相关 actor 写 inbox 提示，不推进 `rooms.head_seq`。错误码与 guard 按契约冻结。
- 网页“新建 Agent”改用 `network_agent_create`（human token），不再用 `network_issue_token` + `network_register` 冒充原子创建；direct Agent 菜单新增“停用 Agent/启用 Agent”，停用前二次确认，`PERMISSION_DENIED` 显示明确提示。独立验收后补充：停用成功后菜单保持打开，展示 `stopped.pending_deliveries`/`claimed_deliveries` 与 `open_tasks`（可折叠任务列表与空态），启用/停用失败在状态行可见。

## 契约、权限与数据变化

- **工具**：新增 `network_agent_create`、`network_agent_management_get`、`network_agents_managed_list`、`network_agent_claim_start`、`network_agent_claim_confirm`、`network_agent_claim_cancel`、`network_agent_delegate_grant`、`network_agent_delegate_revoke`、`network_agent_disable`、`network_agent_enable`；改变 `network_agent_rename`、`network_agent_reissue_token`、`network_agent_archive`、`network_agent_unarchive` 的授权语义；`network_agents_get` 增加 `disabled*` 字段。全部新写工具接受 `request_id`。
- **错误码**：新增 `PERMISSION_DENIED`、`MEMBERSHIP_STALE`、`VERSION_CONFLICT`、`ASSIGNMENT_STALE`、`QUOTA_EXCEEDED`、`REQUEST_EXPIRED`、`INVITE_EXHAUSTED`、`BLOCKED`、`ACTOR_DISABLED`、`PAIRING_INVALID`；A01 路径实际使用 `PERMISSION_DENIED`、`VERSION_CONFLICT`、`REQUEST_EXPIRED`、`ACTOR_DISABLED`、`CLAIM_CONFLICT`、`TOKEN_NOT_REPLAYABLE`、`IDEMPOTENCY_CONFLICT`。
- **Guard**：`0018_p0_guards.sql` 新增 12 张命名 guard 表并登记到 `GUARD_TABLES`；A01 使用 `guard_permission_denied`、`guard_version_conflict`、`guard_actor_disabled`。
- **事件**：新增/启用契约中的管理事件名（`agent_management_bound`、`agent_claim_requested/confirmed/rejected`、`agent_delegation_granted/revoked`、`agent_disabled/enabled`、`credential_reissued`）；rename 复用既有 `profile_updated`。管理事件只写相关 inbox/outbox，不推进房间 head。
- **迁移**：只新增 `0012` 与 `0018` 两个前向迁移，未修改 `0001`–`0011`；新列均可空或带常量默认，无临时表/影子表。
- **客户端**：新建 Agent 改走 `network_agent_create`；direct Agent 菜单新增停用/启用；README 与 CLAUDE 同步新的授权、重放、停用与归档语义。

## 问题与限制

1. **`room_tasks` 没有 `blocked` 状态**：契约 §2.1 规则 5 要求停用把待处理任务置为 `blocked`，但 `0010_room_tasks.sql` 的状态集合只有 `pending|claimed|done|failed`。本期不新增临时状态，停用后任务保持 `pending`/`claimed` 并通过 `pending_work.open_tasks` 展示，绝不静默完成；待 D01 的正式任务/assignment 模型落地时再映射 `blocked`。影响：任务管理者需要读 `network_agent_management_get` 才能看到停用后的未完成任务。
2. **管理权交接未实现**：契约 §6.1 冻结的 `network_agent_transfer_*` 属于 A06；`agent_management_transfers` 表已在 `0012` 建好，本期无工具、无自动认领。当前管理者只能在 A06 合入后发起交接。
3. **设备配对未实现**：`devices`、`device_pairings` 表与 `credentials.device_id` 结构已按 Q02 建好，但 Q02 的工具、事件与网页入口不在 A01 范围；A01 只保证停用/重发会关闭对应 actor 的流。
4. **停用不重写 `room_tasks` 的 claimed 行**：Agent 的凭据被 `ACTOR_DISABLED` 拒绝，已 claim 的投递在同一事务取消，任务行保持原状以便启用后继续或由管理者处理；正式 assignment 的失效/改派留给 D01。
5. **认领过期是惰性判定**：`claim_confirm` 时检查 `expires_at` 并置 `expired`，没有后台扫描任务；符合当前项目“按请求推进状态”的模式，不额外引入调度器。
6. **`test:acceptance` 默认在线/离线时序**：默认配置下 `scripts/acceptance.ts` 的在线断言会因 30 秒等待短于 60 秒活动 TTL 而超时（`reports/BASELINE.md` §3.7 已记录，非 A01 回归）。本次用服务端/客户端一致的 `AGENT_PRESENCE_ACTIVITY_TTL_MS=5000`、`AGENT_PRESENCE_GRACE_MS=2000` 得到 616 项通过。
7. **旧 Agent 需要手动认领**：升级后所有历史 Agent 都是 `unclaimed`，不会按昵称、群主或本地 owner 自动归属；这是 A01 的明确要求，需要管理者与 Agent 各完成一次认领。
