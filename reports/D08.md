## 最终行为与变更

### 1. 任务催办（`src/domain/task-reminders.ts`）

- `remindStaleTasks(db, now)` 扫描 `in_progress` 或仍有负责人的 `blocked` 任务：当前 `current_assignment_id` 必须仍是 `active`，且 `COALESCE(tasks.last_progress_at, assignment.last_progress_at, assignment.accepted_at, assignment.created_at)` 超过 `3 分钟` 没有更新。阈值复用 `LIMITS.taskReminderMs = 3 * 60_000`，与 delivery 提醒同周期。
- 同一 assignment 仍有 `pending` / `claimed` 的 `task_offer` delivery 时跳过任务提醒，避免同一责任者同一窗口收到 delivery 与 task 两条提醒。
- 每轮最多处理 `LIMITS.taskReminderBatchMax = 50` 条；`task_reminders` 以 `(task_id, assignment_id, anchor_at)` 与 `event_key` 双重唯一收敛窗口。`event_key = task_reminder:<task_id>:<assignment_version>:<anchor>`，首次窗口锚点为进度时间，后续锚点为上一次提醒时间；进程重启或并发扫描不会重复提醒。
- 提醒只写当前责任者的 inbox scope `task_reminder` 事件与 `inbox:{actor}` outbox，并推进该 actor 的 `inbox_head_seq`；不创建 task/assignment/delivery、不增加 `pending_count`、不写 room scope 事件、不推进 `rooms.head_seq`、不产生未读。`due_at` 与 `blocked_reason` 只作为提醒元数据，长期值仍以 `tasks` 为准。
- 完成、提交、取消、验收通过后自然停止；人类负责人不要求持续心跳，服务端不会因超时把任务判为失败。
- 接入两处扫描：`src/maintenance.ts` 的维护周期（兜底）与 `src/bun/main.ts` 中与 delivery reminder 共用的 30s 快路径；失败只记录无正文日志，下一轮重新评估。

### 2. 取消加固（`taskCancel`）

- 权限保持“任务创建者、当前负责人、群 owner/管理员”；`reason` 必填，`expected_revision` 继续做 CAS。
- 同一事务内：任务转 `cancelled`、清空 owner/current assignment；撤销当前 assignment（`offered` / `active` / `submitted` 都失效）；关闭该任务所有 `pending` / `claimed` 的 `task_offer` 与 `task_reminder` delivery（按 pending 行数原子递减 `pending_count`）；取消所有 pending 交接提议（`invalidated_by: 'cancel'`）；写 `task_cancelled` room 事件与 outbox。
- 新增 `tasks.cancelled_by`、`tasks.cancel_reason`、`tasks.external_stop_status`。`external_stop_status` 只接受 `confirmed` / `unknown` / `not_required`；省略时进行中或受阻记为 `unknown`，其余状态记为 `not_required`。`confirmed` 是操作者声明，不是服务端验证结果。
- 尽力通知宿主：当前责任者（human 或 Agent）收到 inbox `task_cancelled` 控制事件；每个开放 delivery 写 `delivery_cancelled` 与 `inbox:{actor}` outbox。事件元数据只写 `host_notify_attempted: true`，明确表示“已尝试通知”，不声称外部进程已停止。
- 取消 `submitted` 时保留 `task_submissions` 与 `task_reviews` 全部审计行，任务转 `cancelled` 后不能继续验收；事件记录 `preserved_submission_ids` 与 `preserved_submission_count`。
- 取消与完成/转交/重试并发时由 task revision 闸门、assignment 状态与唯一索引裁决；失败方得到 `CONFLICT` / `VERSION_CONFLICT` / `ASSIGNMENT_STALE` 并读取权威状态。

### 3. 外部执行未知与对账（`src/domain/task-recovery.ts`）

- 新增 `network_task_execution_unknown { request_id, task_id, action_id, reason, assignment_id?, assignment_version?, expected_revision? }`：只允许当前负责人、任务为 `in_progress` 且持有当前 active assignment；把任务转 `blocked` + `blocked_reason = execution_unknown`，递增 revision，并写 `task_progress` 审计。
- `task_external_actions` 以 `(task_id, action_id)` 为主键，记录 `intent`、`state`、`evidence`、创建者与时间。同一任务内 `action_id` 稳定去重；不同任务允许同名 action。重复上报同一 unknown action 返回同一权威快照，不递增 revision。
- 新增 `network_task_execution_resolve { request_id, task_id?, action_id, outcome, evidence, assignment_id?, assignment_version?, expected_revision? }`：只有当前负责人、action 仍为 `unknown` 且任务仍为 `blocked + execution_unknown` 时可记录结论。`confirmed` / `not_executed` 恢复 `in_progress` 并清空阻塞字段；`rejected` 保持 `blocked` 并标记 `execution_rejected`，由负责人决定后续。
- `evidence` 只写 `task_external_actions.evidence`；事件只记录 `outcome` 与 `evidence_bytes`，不写外部结果正文、消息正文或 delivery。
- `network_task_resume` 拒绝 `blocked_reason = execution_unknown` 的任务，必须先走对账，避免用“恢复执行”绕过未知结果。
- 断线、心跳超时或响应丢失不做自动重跑；服务端没有基于租约过期的外部执行补偿路径。

### 4. 显式重试/重派（`taskRetry`）

- 新增 `network_task_retry { request_id, task_id, reason, assignee_actor_id?, expected_revision? }`：只有创建者、群 owner/管理员可用，只接受 `failed` 任务，`reason` 必填并做 revision CAS。
- 同一事务撤销所有 `offered` / `active` 旧 assignment、关闭该任务所有 pending/claimed 任务投递、取消 pending 交接、递增 `task_revision`；旧负责人的 progress/submit/继续派活资格随 assignment 失效。
- 指定 `assignee_actor_id` 时生成新的 `assignment_version = max + 1`，任务回到 `offered`，Agent 候选生成新投递与必要的新卡片，human 候选收到持久个人通知；省略时任务回到 `unassigned`，下一次 offer 使用新的 assignment_version。重试写 `task_retried` room 事件，记录 previous assignment 与新版本。
- 外部副作用结果未知时不提供自动重跑；必须先 `network_task_execution_unknown` / `network_task_execution_resolve` 对账。

### 5. 重启与补读

- 任务可见性完全来自持久 `tasks` / `task_assignments` / `events` / `outbox`；服务重启不恢复进程内栈或定时器状态。
- `src/realtime/stream.ts` 新增 `task_reminder` → `source: "task.reminder"`、`kind: "reminder"`、`attention: "action_required"`；`task_retried` / `task_execution_unknown` / `task_execution_resolved` 继续映射为 active human 的 `task.updated` informational。
- 断线重连后可用 `network_task_summary` / `network_task_list` 读取权威任务；`network_sync` inbox 补读 `task_reminder`，room scope 补读任务事件；outbox 由新进程的请求 fast-path 或 30s 扫描补发。

### 6. 工具面、网页与文档

- 任务工具 29 → 32，整体工具面 111/102 → 114/105（Drive 与房间文件开关）。新增 3 个写工具；`network_task_cancel` 增加可选 `external_stop_status`。
- `taskSchema` 增加 `cancel_reason`、`cancelled_by`、`cancelled_by_name`、`external_stop_status` 与 `can_retry` / `can_report_execution_unknown` / `can_resolve_execution`；新增 `taskExternalActionSchema` 与 `taskRecoveryResultSchema`。
- 网页新增 `src/web/chat-task-recovery-script.ts`（124 行）：失败重试、标记执行未知、记录对账结论；取消入口增加外部停止状态下拉；详情显示取消原因、操作者与外部执行状态。`chat-tasks-script.ts` 保持 999 行，DOM id/class 与既有行为不变。

## 契约、权限与数据变化

- 契约版本仍为 `webots-p0-v1`；没有新增错误码，沿用 `ASSIGNMENT_STALE` / `VERSION_CONFLICT` / `PERMISSION_DENIED` / `CONFLICT` / `NOT_FOUND` / `REQUEST_EXPIRED` / `IDEMPOTENCY_CONFLICT` / `TOKEN_NOT_REPLAYABLE`。
- 迁移 `0035_task_recovery.sql`：
  - 目的：持久化任务提醒窗口、外部动作对账与取消审计。
  - 权威状态：`tasks.status` / `revision`、`task_assignments`、`deliveries` 仍是业务权威；新表不复制状态。
  - 约束/索引：`task_reminders.event_key` 唯一、`(task_id, assignment_id, anchor_at)` 唯一；`task_external_actions` 主键 `(task_id, action_id)`、action_id 索引；`tasks.external_stop_status` 只接受三个枚举值或 NULL。
  - 旧数据映射：不改写既有行；旧任务新列为 NULL，旧任务没有提醒窗口/外部动作，首次扫描或调用时建立。
  - 恢复方式：回退应用版本时旧代码忽略新增表与列；不删除、不重建已发布表，不改写既有行。
- 权限：取消仍由创建者/当前负责人/群 owner/管理员执行；重试由派发者执行；外部执行未知/对账由当前负责人且持有 active assignment 执行。`confirmed` 外部停止状态仅为操作者声明。
- 通知：任务事件仍为 human-only `task.updated` informational；新的 `task_reminder` 是当前责任者 inbox 提醒，不创建 delivery、不增加 `pending_count`、不推进 `rooms.head_seq`。
- 客户端影响：`taskSchema` 新增可空字段与三个 `can_*`；旧客户端忽略新字段即可。新增工具需要客户端显式调用；`network_task_cancel` 新增可选参数，旧调用不变。

## 问题与限制

1. **没有公开的 `failed` 入口**：D08 只提供 `network_task_retry`，没有新增 `network_task_fail`（D01 已退休旧看板 fail 语义）。因此 T02 的 retry 用例在真实迁移与 domain 层构造 `failed` 持久行后验证，没有通过公开 MCP 工具制造 failed。若后续 D 组需要 Agent 主动声明失败，应单列工具与授权验收，不能复用旧 `network_task_fail`。
2. **外部停止是尽力而为**：服务端只会写 inbox/outbox 控制通知并记录操作者声明的 `external_stop_status`，没有宿主/适配器来实际杀进程或撤销远端操作。`confirmed` 不是服务端保证，报告和技能正文均明确这一点。
3. **外部系统查询由调用方完成**：本仓库没有具体外部 Issue/CI 适配器；`network_task_execution_resolve` 接收查询或人工证据并持久化，不自动访问目标系统。`action_id` 在不同任务内可重复，省略 `task_id` 且 action 跨任务存在时要求显式 `task_id`。
4. **提醒语义**：有负责人的 `blocked` 任务也会收到催办（用于推动解除阻塞或对账），`owner_lost_eligibility` 等 owner 为空的任务不会提醒；execution_unknown 的提醒只提示对账，不会自动改状态。人类负责人不要求心跳。
5. **旧 `task_reminder` delivery**：D08 本身不创建该类 delivery；取消会关闭历史/其他生产者留下的 `task_reminder` 投递，迁移不改写它们。
6. **重启验收为自托管临时实例**：T04 在验收进程内启动独立 Bun 与临时 `DATA_DIR`，停止后用新 SQLite/D1 连接写入提醒，再启动新进程验证补读；它不重启外部承担生产流量的实例。独立验证者应在集成环境复核 `PUBLIC_ORIGIN`、TLS 与真实部署重启。
7. 本轮 `test:web` 通过既有 1950 项；D08 网页新增入口通过协议静态断言与全量网页回归覆盖，未新增 Playwright 交互脚本。
