## 最终行为与变更

### 1. 持久模型与生命周期

- `migrations/0024_room_owner_transfers.sql` 新增 `room_owner_transfers`：
  - `transfer_id`、`room_id`、`from_owner_id`、`to_actor_id`、`status`（`pending|accepted|rejected|cancelled|expired`）、`version`、`target_role_revision`、`invalid_reason`、`created_at`/`updated_at`/`expires_at`、`responded_at`/`responded_by`。
  - `CHECK (from_owner_id <> to_actor_id)`；部分唯一索引 `idx_room_owner_transfers_pending` 保证同一群至多一条 `pending`。
  - 新增闸门表 `guard_owner_transfer_stale`；`GUARD_TABLES` 与 `runner.ts` 同步，映射为 `CONFLICT`（“群主转让提议状态已变化，请刷新后重试”）。
- 同一迁移重建 `room_management_audit` 并保留全部旧行，动作 CHECK 追加 `owner_transfer_proposed|accepted|rejected|cancelled|expired`；G03 已写入的 `owner_transferred` 继续可读。
- 默认有效期 `LIMITS.roomOwnerTransferTtlMs = 24h`，由 `expires_at` 持久化；读取、响应与发起都以数据库时间判定，不依赖客户端时钟。
- 过期或目标离群/被移除的 pending 行在读取时视为不存在（`loadOwnerTransferView` 的 JOIN 条件），并在下一次发起时由 `expireStaleProposalsStatement` 在同一事务内收敛为 `expired`（`invalid_reason` 为 `expired` 或 `target_inactive`）。

### 2. 服务端授权、幂等与原子换主

- `roomOwnerTransferPropose`：仅当前 owner（`transfer_owner` 能力）可调用；目标必须是 active、非 owner 成员；可选 `expected_role_revision` 预检。先鉴权后 `resolveReplay`，同一 `request_id` 重放返回同一提议；已存在有效 pending 时 `CONFLICT`；写入提议、room scope 事件、`room:{id}` outbox、目标 inbox 头、成员版本事件与管理审计。
- `roomOwnerTransferRespond`：只有目标本人可响应，其他身份返回 `NOT_FOUND`。接受时在同一 `db.batch()` 内复核：
  - 提议仍 `pending`、未过期、`version` 等于 `expected_version`；
  - 群仍存在且为 group，`rooms.owner_id` 仍是原 owner；
  - 原 owner 仍是 active owner，目标仍是 active 非 owner；
  - 目标 `role_revision` 等于发起时记录的 `target_role_revision`；
  - 通过后更新提议为 `accepted`、原 owner 降为 `member`、目标升为 `owner`、双方 `role_revision + 1`、`rooms.owner_id` 更新，并写双方 `owner_transfer_accepted` 审计。
  - 拒绝只关闭提议与写审计，不改任何角色；目标拒绝后原 owner 继续负责。
- `roomOwnerTransferCancel`：只有发起人（原 owner）可取消；复核 `expected_version`、仍在位与未过期；只关闭提议，不改变角色。
- 重放先于状态/版本检查：重复接受同一 `request_id` 返回同一结果；提议已接受或取消后，新 `request_id` 不能再次生效（`CONFLICT`）。
- 转让只改变群内角色；不写 `agent_managements`、不改任务负责人、设备凭据或外部资源权限。不在 owner 离线时自动选举。
- 发起后原 owner 仍按 G03 的 owner 离群 guard 执行：群内还有其他 active 成员时 `network_room_leave` 返回 `CONFLICT`，不能用“已发起转让”为理由直接离群。

### 3. MCP 工具、输出与通知

- 新增 `network_room_owner_transfer_propose`、`network_room_owner_transfer_respond`、`network_room_owner_transfer_cancel`；输出均为完整 `roomDetail`，包含 `owner_transfer`。
- `network_room_owner_transfer` 保留为 propose 兼容别名，不再直接切换 owner；描述明确要求响应工具。
- `network_room_members_update.transfer_owner_to` 仍被 schema 接收，但领域层立即返回 `INVALID_ARGUMENT`（“直接转移群主已移除，请使用 network_room_owner_transfer_propose”），不静默降级。
- `room_get` 新增 `owner_transfer: { transfer_id, room_id, from_owner_id/name, to_actor_id/name, status, version, expires_at, created_at, can_accept, can_reject, can_cancel } | null`；`can_*` 只描述当前查看者，不替代服务端 guard。
- `src/realtime/stream.ts`：
  - room scope：`room_owner_transfer_proposed` → `room.membership`/`owner_transfer_pending`，`rejected|cancelled|expired` → `owner_transfer_closed`，`accepted` → `owner_changed`；

- `src/mcp/skill.ts` 更新群角色段落，说明 propose → 目标 respond、24 小时、接受前原 owner 仍负责、cancel 与兼容别名。

## 契约、权限与数据变化

- **迁移**：仅新增前向迁移 `0024_room_owner_transfers.sql`，未修改既有迁移；新库按序应用、旧库升级由 `feedback-unit` 覆盖，旧审计行完整保留。
- **新 guard**：`guard_owner_transfer_stale`，错误映射 `CONFLICT`；未新增错误码，复用 `CONFLICT`、`VERSION_CONFLICT`、`REQUEST_EXPIRED`、`NOT_OWNER`、`PERMISSION_DENIED`、`INVALID_ARGUMENT`、`NOT_FOUND`。
- **工具**：新增 3 个，保留 `network_room_owner_transfer` 兼容别名；工具总数 77 → 80（关闭 Drive 72 → 75）。README、`docs/code-index.md`、协议断言同步更新。
- **输出 schema**：`roomDetailSchema` 新增可空 `owner_transfer`；管理审计动作枚举扩展。
- **事件**：新增 `room_owner_transfer_proposed|accepted|rejected|cancelled` 的 room scope 事件与 inbox 事件；预留 `expired` 映射但当前无显式写入方（见限制）。
- **命名偏差**：契约基线使用 `from_actor_id`，实现采用更明确的 `from_owner_id`；契约冻结审计动作 `owner_transfer_propose|accept|reject`，实现沿用 G03 的过去式命名 `owner_transfer_proposed|accepted|rejected`，并额外使用 `cancelled|expired`。语义一致，但验证者应以实际迁移与代码为准。
- **权限**：群主转让只影响 `rooms.owner_id`、`room_members.role`/`role_revision` 与审计；不改变 `agent_managements`、任务负责人、delivery、凭据或外部资源权限。
- **网页**：成员弹窗新增面板与样式；缓存新增 `ownerTransfer` 字段；无凭据或页面权限绕过。

## 问题与限制

1. **真实过期无法在验收中推进时钟**：G05-T02 只能断言返回的 `expires_at` 落在 24 小时窗口，无法在 24 小时后再次运行同一提议；过期读取、接受失败与下次发起收敛由代码路径与事务 guard 保证，未做时间旅行测试。独立验证若需要，可用可控时钟或直接 SQL 把 `expires_at` 改到过去后复验。
2. **没有后台过期扫描任务**：过期只在读取时隐藏、在下一次发起时持久收敛为 `expired`；`room_owner_transfer_expired` 的 stream 映射已存在但没有写入方。若运营需要主动通知，需增加定时任务或复用现有 outbox drain，另行评审。
3. **群解散（G06）未实现**：任务要求的“解散使提议失效”无法在当前仓库端到端验证。`loadOwnerTransferView`/响应 guard 目前以 group 存在、`rooms.owner_id` 与成员状态判定；G06 落地时必须补解散标记条件并重跑 T02。
4. **原 owner 离群依赖 G03 guard**：没有新增“提议未决时禁止 owner 离群”的专用列；当前行为由 G03 的“owner 有其他 active 成员时不能离群”保证。若 G06 引入空群或解散前退群路径，需要重新评估。
5. **命名偏差**：见“契约、权限与数据变化”；不影响行为，但独立验证应以实际迁移、工具签名与错误码为准。
6. **网页与服务的同步依赖统一 stream**：网页多端一致性由 stream 触发的 `room_get` 刷新保证；断线重连期间仍以刷新后的服务端状态为准，不使用本地乐观换主。
