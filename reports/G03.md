## 最终行为与变更

### 1. 角色模型与唯一授权入口

- `migrations/0020_group_roles.sql`：重建 `room_members`，角色收紧为 `owner | admin | member`，新增 `role_revision` 与 `updated_at`，保留原有行与主键；部分唯一索引 `idx_room_members_one_owner` 保证每个房间最多一个 active owner。`rooms.owner_id` 与 owner 成员行在同一事务内维护，二者不会分叉。
- `rooms` 新增 `policy_revision`、`member_message_policy`、`member_invite_policy`、`member_task_policy`、`announcement`、`announcement_revision` 与公告更新人/时间。默认值为 `members` / `owner_admin` / `members`，与实现前的行为保持一致：普通成员可发言、可建任务，邀请仍限 owner/管理员。
- 新增 `src/domain/room-access.ts` 作为**唯一授权判定**：`roomCapabilitiesFor`、`memberActionsFor`、`roomPolicies`、`loadRoomAccess`/`requireRoomAccess`、`requireGroupAccess`、`requireTargetMember`、`requireExpectedRoleRevision`。JS 能力表与事务 guard 共用同一组 `CAPABILITY_PREDICATES`（别名 `r`/`m`）以及目标谓词，避免预检与提交判定漂移。
- 能力共 10 项：`send_message`、`create_task`、`invite_members`、`remove_members`、`manage_admins`、`manage_announcement`、`manage_policy`、`transfer_owner`、`approve_joins`、`view_role_history`。`manage_admins`、`manage_policy`、`transfer_owner` 为 owner-only；`remove_members`、`manage_announcement`、`approve_joins`、`view_role_history` 为 owner/admin；`send_message`/`create_task`/`invite_members` 再受群策略约束。
- **群角色不授予 Agent 所有权或外部权限**：`room-access.ts` 只读 `rooms` 与 `room_members`，不读 `agent_managements`、设备凭据或联系人。Agent 担任管理员不会改变其管理者、`manage_agent` 委托或凭据重发资格。

### 2. 所有写入口共享同一判定

- 消息：`src/domain/messages.ts` 的 `messageGuardStatements` 增加 `send_message` 能力 guard；任务：`src/domain/tasks.ts` 的 `taskAdd` 增加 `create_task` 能力 guard。两者都在 `runIdempotent` 的同一 `db.batch()` 内执行，策略在提交时重新判定。
- 成员增删：`roomMembersUpdate` 先 `loadRoomAccess` 预检 `invite_members`/`remove_members`，再按目标计算 `memberActionsFor`；管理员只能移除普通成员，任何角色都不能移除 owner，owner 也不能通过该工具移除自己。添加成员、移除成员、主动退群都会推进目标 `role_revision` 并写管理审计。
- 角色任免：`roomRoleSet` 仅 owner 可调用，目标必须是 active 非 owner 成员；任免与审计、事件、outbox 在同一事务提交。
- 转让：`roomOwnerTransfer` 仅当前 owner 可调用，目标为 active 非 owner；新旧 owner 角色、`rooms.owner_id` 和审计在同一事务完成。旧 `network_room_members_update.transfer_owner_to` 仍兼容，但**必须同时给出 `expected_role_revision`**；未给出的旧客户端会收到 `INVALID_ARGUMENT`，这是有意的安全收紧。
- 策略与公告：`roomPolicySet` 为 owner-only；`roomAnnouncementSet` 为 owner/admin。两者分别用 `expected_policy_revision`、`expected_announcement_revision` 做乐观锁，冲突返回 `VERSION_CONFLICT`。
- 审计：`room_management_audit` 追加写 `member_added`、`member_removed`、`member_left`、`admin_appointed`、`admin_revoked`、`owner_transferred`、`policy_updated`、`announcement_updated`，记录前后角色/状态、预期版本、结果版本、操作者与 `request_id`，不保存消息正文或凭据。
- 重放：每个写入口先做授权预检，再进入 `runIdempotent`；命中同一 `request_id` 且 payload 相同时，`resolveReplay` 在**鉴权通过之后**返回已存结果，跳过会随首次写入失效的版本检查。被撤销的管理员重放旧请求得到 `PERMISSION_DENIED`/`NOT_OWNER`，而不是缓存成功；同角色重复任免仍是幂等的无副作用结果。
- 错误映射：owner-only 能力不足返回 `NOT_OWNER`，管理员/普通成员能力不足返回 `PERMISSION_DENIED`；版本不匹配返回 `VERSION_CONFLICT`（guard 消息“群角色/群策略/群公告版本已变化”）；并发撤销与移人由同一事务的 guard 按提交序裁决，不会半提交。owner 退群在同一 `db.batch()` 内用 `guard_owner_transfer_required` 复核“仍有其他 active 成员”，并发加人时返回 `CONFLICT`，不会留下无 owner 的非空群。

### 3. MCP 工具与输出

- 新增工具：`network_room_role_set`、`network_room_owner_transfer`、`network_room_policy_set`、`network_room_announcement_set`、`network_room_role_history`（只读）。
- `network_room_get`/成员列表输出新增 `my_role`、`my_role_revision`、`policy_revision`、`policies`、`announcement`、`announcement_revision`、`announcement_updated_at/by`、`capabilities`；每个成员新增 `role_revision` 与 `actions{can_remove,can_set_admin,can_revoke_admin,can_transfer_owner}`。输出只描述当前身份可见的能力，不替代服务端 guard。
- `network_room_role_history` 分页读取审计，默认 20、上限 100（`LIMITS.roomRoleHistoryPageDefault/Max`），仅 owner/admin 可读。公告正文上限 4 KiB（`LIMITS.roomAnnouncementBytes`）。
- 工具描述明确写出：管理员不能任免管理员、不能移除 owner、不能转让；群角色不影响 Agent 管理关系与凭据。技能正文同步更新群角色、`room.membership` 的 `role_changed`/`owner_changed`/`policy_updated`/`announcement_updated`，并说明同群管理员仍不能重发其他 Agent 凭据。

### 4. 通知与网页

- `src/realtime/stream.ts` 将 `room_role_changed`、`owner_transferred` 映射为 `room.membership` 的 `role_changed`/`owner_changed`（自己被降级时 `action_required`），将 `room_policy_changed`、`room_announcement_updated` 映射为提示型变更。角色、策略、公告写入都向 `room:{id}` 写 outbox，页面收到后重读房间；不推进 `rooms.head_seq`，不制造未读。
- 网页（`src/web/chat-members-script.ts`）：不再用 `isGroupOwner()` 猜测权限，改为读取 `room.capabilities`；群主/管理员/普通成员与 Agent 显示不同角色标签；按 `member.actions` 渲染“设为管理员 / 撤销管理员 / 转让群主 / 移出群聊”。错误映射 `NOT_OWNER`、`PERMISSION_DENIED`、`VERSION_CONFLICT`，操作后串行刷新成员与房间。
- 新增 `src/web/chat-announcement-script.ts`：聊天头部公告条与“公告/查看公告”入口；owner/admin 打开编辑弹窗，提交 `network_room_announcement_set` 并携带当前 `announcement_revision`；普通成员只读查看，输入框 `readonly` 且不显示保存。公告上限由服务端 `LIMITS` 注入，超限在页面提示且不提交。
- 入口隐藏只改善体验，不构成授权：直接调用工具仍按上述 guard 拒绝（G03-T01/T03 覆盖）。

### 5. 专项验收

- `scripts/lib/group-role-acceptance.ts` 提供 `runGroupRoleAcceptance()`，由 `scripts/acceptance.ts` 在既有端到端流程后执行：
  - **G03-T01**：普通成员直接调用管理工具被拒绝（`NOT_OWNER`/`PERMISSION_DENIED`）；owner 任命管理员；同一 `request_id` 重放幂等；管理员不能转让、任免管理员、改策略、移除 owner；管理员可移除普通成员、维护公告并留下审计；撤销后重放旧移除请求得到 `PERMISSION_DENIED`。
  - **G03-T02**：`Promise.allSettled` 并发执行“owner 撤销管理员”与“该管理员移除成员”，按事务提交序裁决，失败方无半提交，审计与最终角色一致；过期 `expected_role_revision` 返回 `VERSION_CONFLICT`。
  - **G03-T03**：同一身份分别走 MCP 工具与网页使用的原始 JSON-RPC 路径，公告、审计与越权错误码完全一致；owner 可创建 Agent、任命其为管理员，该 Agent 获得 `remove_members` 但不获得 `manage_admins`/`transfer_owner`；管理员 Agent 仍不能重发或改名其他 Agent 的凭据；`management_get` 的 manager/can_manage 不因群角色变化。
  - **G03-T04（独立验收后新增）**：owner 有其他 active 成员时退群返回 `CONFLICT`；owner 是唯一 active 成员时退群成功，空群不能再加人；40 轮并发 `owner leave × add member` 中两者不能同时成功，任何非空群都存在且仅存在一个 active owner，`rooms.owner_id` 与 owner 成员行一致。
- `scripts/verify-web.ts` 新增 2b-5 段：owner 看到公告入口、成员角色与“设为管理员”，点击后服务端角色写入并出现“撤销管理员”；管理员看到“移出群聊”但没有任免/转让入口，也不出现“只有群 owner”提示，可编辑公告且公告显示在聊天区；撤销后入口消失；普通成员只能只读查看公告。

## 问题与限制

1. **入群审批流程属于 G02**：本任务只提供 `approve_joins` 能力位与授权基座，没有实现邀请/申请/审批工具或页面。G02 接入时应复用 `room-access.ts` 的 `requireRoomAccess` 与 guard，不另写判定。
2. **解散群不在本任务**：owner 与其他 active 成员同群时必须先转让才能退群；owner 是唯一 active 成员时允许退群并留下空群（`owner_id = NULL`，无成员可孤立）。群解散属于 G05。
3. **审计读取仅限 owner/管理员**：没有公开审计、导出或保留期策略；分页上限 100。需要更细粒度审计时按后续任务扩展。
4. **公告为纯文本**：上限 4 KiB，不支持富文本/附件；公告更新只广播提示，不产生消息、delivery 或未读。
5. **策略只影响后续操作**：修改 `member_*_policy` 不会追溯撤销已发送消息、已创建任务或已领取的工作；任务/消息写入时按当时策略判定。
6. **旧 `transfer_owner_to` 为破坏性收紧**：必须带 `expected_role_revision`。仓库内网页与验收已迁移；外部客户端需同步升级。
7. **迁移重建 `room_members`**：会产生一次表复制与短暂写锁，只支持前向迁移；未在生产环境执行，部署时仍需按发布流程迁移。
8. **在线时序门禁**：`test:acceptance` 使用与 A01/A03 报告一致的短 presence 参数（grace/TTL 1200ms），默认 30s/60s 下部分在线断言会超时，属既有基线问题而非 G03 回归。
9. **契约基线名称已对照**：G03 实际工具名已写入 `reports/CONTRACT_BASELINE.md` 的 6.3 表；G02/G05/G07 的规划名仍不代表已实现。
