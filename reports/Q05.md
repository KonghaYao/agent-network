## 最终行为与变更

### 1. 自托管并发验收入口

`scripts/verify-q05.ts` 启动独立 Bun 实例（随机唯一 `PORT`、独立 `DATA_DIR`、`PUBLIC_ORIGIN` 与 `AGENTNET_URL` 一致、短 presence 窗口、`ENVIRONMENT=test`），使用固定种子 `Q05_SEED=20261108`（可覆盖）驱动 10 个场景。脚本结束时停止进程并删除临时数据目录；失败输出包含场景、轮次、种子、最后 40 个 `request_id` 与单轮复现命令。

模块职责：

- `scripts/lib/q05-harness.ts`：临时实例/重启、真实 MCP `tools/call`、并发放行 `burst`、权威 SQLite 读取、每轮 10 项全局不变量审计、SSE 订阅、HTTP 响应丢失代理、场景清理。
- `scripts/lib/q05-fixture.ts`：U1–U5 与 B1–B3、每个 human 的 3 个自有 Agent、双向好友、主群与 direct 会话。
- `scripts/lib/q05-messages.ts`：同 request_id / 同 client_message_id 的 100 并发、冲突正文、正文与 seq 一致性。
- `scripts/lib/q05-claims.ts`：公开领取 100 并发、指定 offer 100 并发接受、失败方读取真实 owner。
- `scripts/lib/q05-task-race.ts`：转交 × 旧提交/取消/移除四路竞争；验收 accept × return、重复 accept 与退回路径。
- `scripts/lib/q05-files.ts`：上传/绑定/成果提交 × GC × 成员移除；配额不足与恢复。
- `scripts/lib/q05-contacts.ts`：申请 × 接受 × 拉黑；确定性的“拉黑先到”路径。
- `scripts/lib/q05-devices.ts`：配对、活跃 SSE、撤销 × 工具调用；主设备与其他身份对照。
- `scripts/lib/q05-agents.ts`：管理权交接 × 旧管理者 100 次重发；确定性“先重发后交接”。
- `scripts/lib/q05-owners.ts`：群主转让 × 退群/解散/移除；按固定种子轮换群主。
- `scripts/lib/q05-faults.ts`：事务回滚、提交后响应丢失、outbox、重启、外部结果未知、凭据重连。

### 2. 每轮全局审计

每轮结束读取权威表检查：单 active assignment、单群主、单 pending submission、无双 active 好友关系/拉黑、无悬挂 `file_reference`、任务卡唯一、Agent 单有效运行凭据、无重复任务投递行、accepted 任务有独立验收记录。失败即计入该轮失败，不以 HTTP 200 数量推断正确。

### 2.2 故障注入结果

| 故障组 | 注入点 | 实际观察 |
|---|---|---|
| transaction-rollback | 事务中途唯一键冲突；无效附件任务 | 同 client_message_id 不同正文返回 `IDEMPOTENCY_CONFLICT`；冲突正文未落库、operations 未残留；原消息与事件仍唯一；无效附件任务整体回滚、无任务行 |
| response-loss | 测试进程 HTTP 代理：上游完整提交后打断响应体 | 客户端读不到响应但业务已提交；同 request_id 重试返回同一 message_id/task_id；消息/任务卡/事件均唯一 |
| outbox-replay | 已发布事件回拨为 pending；持锁 processing + 同一 DATA_DIR 重启 | 重启后补发，事件仍只有 1 条，SSE 按 event_id 去重后仅 1 条；持锁期间不提前发布、不丢事件，租约到期后补发且不复制事件 |
| restart-recovery | 停止进程后用新进程读同一 DATA_DIR | 任务状态/owner/进度、任务提醒、投递提醒、claimed 投递、房间历史全部恢复；重复扫描不重复提醒 |
| execution-unknown | `network_task_execution_unknown` 后重启 | 重启后仍 blocked/`execution_unknown`、action 仍 unknown、无新投递；`resolve confirmed` 后恢复 in_progress 且不重复副作用；action 结论不可改写 |
| credential-reconnect | 断流期间写入、重启、按游标补读；撤销设备 | 离线消息按 event_id 去重后全部补齐；撤销凭据不能读/写/收流，活跃流关闭；主设备正常 |

## 复现与重放

```bash
# 全量 100 轮/场景；固定种子
Q05_SEED=20261108 bun scripts/verify-q05.ts

# 只重放某个失败轮次（脚本仍会先建立夹具）
Q05_SEED=20261108 bun scripts/verify-q05.ts --scenario=claim-accept --round=37

# 快速回归（每场景 20 轮）
Q05_ROUNDS=20 bun scripts/verify-q05.ts

# 记录机器可读摘要（不含 token/正文）
Q05_SUMMARY_PATH=reports/evidence/q05/q05-summary.json bun scripts/verify-q05.ts
```

固定种子决定候选顺序、四路调用的放行顺序与轮换身份；操作系统调度仍可能改变最终胜者，但每轮不变量必须成立。失败输出记录场景、轮次、种子、最后 40 个 `request_id` 与复现命令。原始输出在 `/tmp/q05-run.log`（临时文件，不作为仓库证据）；仓库证据为 `reports/evidence/q05/q05-summary.json`。

无生产代码、工具 schema、权限语义、迁移或共享契约变化。故障注入只在测试进程的 HTTP 边界（响应体打断）、临时 SQLite 夹具（outbox 状态、过期时间、提醒时间）与同一 `DATA_DIR` 的新进程上完成，不修改服务端业务分支。

## 问题与限制

1. **Q05 范围内未发现并修复 P0/P1 产品缺陷。** 开发过程中出现的限流/活跃房间上限碰撞来自“每轮建新群/反复移入”的测试夹具设计；改为按 owner 轮换、固定群复用与独立提醒 Agent 后，100 轮全量通过。这些不是产品缺陷。
2. **Q05-OBS-01（P1，Q06 容量范围，未修复）**：`activeRoomsPerActor=200` 的闸门统计 `room_members` 中 `status='active'` 的成员关系，未排除 `rooms.dissolved_at IS NOT NULL` 的已解散群。测试夹具在累计约 200 个群（其中大量已解散）后，同一 owner 的 `network_room_create` 返回 `CONFLICT`（“活跃房间数量达到上限”）；已解散群仍占用额度。复现方式为同一 human 反复建群并解散，直到 `room_members` 中该 actor 的 active 行达到 200 后再建群。该行为属于 Q06 容量与长期数据设计，本轮不改闸门语义，交由 Q06/集成人裁决。
3. **竞争分布是固定种子下的真实结果，不代表所有分支每轮都会胜出**：review 混合竞争 100 轮均由 accept 胜出（另有 100 次独立退回路径验证）；contacts 混合竞争 100 轮均先接受后拉黑（另有 100 次“拉黑先到”验证）；agent transfer 并发重发成功 0 次（另有 50 次确定性“先重发后交接”验证）。这些补充路径保证两个终态可达，但固定种子的混合竞争分布已如实记录。
4. **P1 缺口未实现、未伪造通过**：M05 撤回/转发、M09 群音视频/真实 TURN、Q03 外部 Issue/员工绑定与结果回写、Q06 容量/告警/备份恢复，以及 A02/A04/G04/M01/M04/M08 的未实现部分。E19（M09）、E20（Q03）、E21（Q06）不在本轮签收范围。
5. **outbox 故障是受控模拟**：没有生产 drain 开关；通过持锁 `processing`、租约到期与同一 DATA_DIR 重启验证“不丢、可补发、按 event_id 去重”。真实崩溃窗口的覆盖依赖同一持久化 outbox 语义，报告不声称做过进程级 kill -9 的随机窗口注入。
6. **外部结果未知只覆盖 D08 本地状态机与重启持久化**，没有 Q03 外部适配器，因此不验证远端 action 查询或远端拒绝。
7. 本轮未部署、未访问生产、未创建 PR；独立验证者应在集成 SHA 上重跑 Q05 全量、上述门禁，并复核 P1 缺口未被误报为完成。
