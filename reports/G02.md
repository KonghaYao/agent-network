## 最终行为与变更

### 1. 邀请模型与链接

- `migrations/0027_group_invite_links.sql` 不另建同义邀请表，继续以 `room_invitations` 为唯一权威来源。`kind = 'link'` 时 `target_actor_id` 为空，`token_hash` 保存带域分隔前缀的 SHA-256 摘要，明文 `invite_key` 只在创建响应出现一次；`kind = 'direct'` 仍由 G01 的定向邀请语义处理。
- `network_room_invite_create` 不传 `target_actor_id` 时创建可分享链接：默认 7 天、默认 20 次成功加入、单群同时有效链接上限 20。调用方可指定 `expires_in_ms`（1 秒至 30 天）与 `max_uses`（1–100）。阈值全部来自 `src/contracts/limits.ts` 的 `LIMITS`，调用点不复制常量。
- 创建响应返回 `invitation`、一次性 `invite_key` 与 `${PUBLIC_ORIGIN}/j/<key>` 的 `share_url`；之后的列表、预览与撤销响应都不返回明文 key 或分享 URL。服务端不能恢复旧二维码，只能确认其摘要对应的邀请状态。
- 定向邀请固定 1 次使用，要求目标为好友并复核拉黑关系，不生成 `invite_key`/`share_url`。邀请对象只含群引用、邀请人、有效期、次数与撤销状态，不含任何 actor 登录凭据。
- `network_room_invite_revoke` 支持邀请人（`member_invite_policy = 'members'` 时）、owner 与 admin 立即撤销，使用 `expected_revision` 做乐观并发；同一事务把该邀请的 pending 入群申请置为 `expired`，写 `invite_revoked` 审计与 `room_invitation_revoked` 房间事件。

### 2. 打开、确认与审批

- `GET /j/:inviteKey` 由 `src/app.ts` 校验 key 形状（`[A-Za-z0-9_-]{16,64}`）后渲染 `src/web/join.ts`，响应 `cache-control: no-store`；页面只显示群名、人数、邀请人、有效期、审批策略与“邀请码有效不等于已加入”的说明。页面不内联邀请人或打开者的 token，也不读取任何群消息。
- 打开者先用本机 Bearer 身份调用 `network_room_invite_get { invite_key }` 获取最小预览。预览不含消息、历史或凭据字段；`next_step` 稳定给出 `share | invalid | member | removed | blocked | pending_approval | request | join`，`status` 派生 `expired`/`exhausted`/`revoked` 等状态，`can_respond` 只对可继续处理的邀请为 true。
- 确认通过 `network_room_invite_respond { invitation_id, invite_key }`。群策略为 `open` 时在同一事务消费一次使用并写入 active 成员；策略为 `approval` 时只创建 pending 申请，不写 `room_members`、不消费次数、不增加成员数，打开者此时仍不是成员。
- `network_room_join_request_list` 只允许 owner/admin 读取 pending 申请；`network_room_join_request_respond` 批准时在同一 `db.batch()` 内重新检查邀请 `pending`、有效期、剩余次数、邀请版本、拉黑、申请人 `removed` 状态与 100 人 active 上限，然后消费一次邀请、写 active 成员、审计与通知。拒绝不消费邀请。
- 因审批策略被拒绝或失效的申请仍保留行，但按邀请状态派生为 `expired`，`can_approve = false`；审批者不会面对无法执行的按钮。
- 被移除成员不能复用旧链接：链接加入路径对 `room_members.status = 'removed'` 返回 `CONFLICT`，预览 `next_step = 'removed'`。重新加入必须由 owner/admin 新建定向邀请；定向邀请只在 `created_at >= member.updated_at` 时可用。重新加入递增 `member_generation`，历史下界是本次加入事件，移出前消息不可见。

### 3. 并发与一致性

- 链接使用次数与成员写入在同一事务完成：`consumeInvitationStatement` 用条件更新把 `used_count` 加一，并按 `kind = 'link'` 与剩余次数把状态落为 `pending` 或 `exhausted`，随后成员写入、审计与事件同批提交。
- 两名申请人竞争最后一格时，`guard_join_request_stale` 与邀请版本条件裁决，只有一个事务成功；失败方返回 `CONFLICT`，邀请最终状态为 `exhausted`，`used_count` 与 active 成员增量一致，失败申请保持 pending 行但不可再批准。
- 错误映射集中在 `src/storage/transactions/runner.ts`：`invitationStale`/`joinRequestStale` → `CONFLICT`，`inviteExhausted` → `INVITE_EXHAUSTED`，`requestExpired` → `REQUEST_EXPIRED`，`roomFull` → `ROOM_FULL`，`roomInviteLimit` → `QUOTA_EXCEEDED`。迁移新增 `guard_join_request_stale` 与 `guard_room_invite_limit`，并同步 `GUARD_TABLES`。
- 所有幂等写仍经 `runIdempotent`；重复 `request_id` 返回首次结果，重复打开链接收敛到同一条 pending 申请。

- **迁移**：`0027_group_invite_links.sql` 新增 `room_join_requests`、`guard_join_request_stale`、`guard_room_invite_limit`；重建 `room_management_audit` 的 `action CHECK` 以加入 5 个审计动作，并恢复审计索引。`scripts/lib/feedback-unit.ts` 迁移清单同步到 `0027`。

- **状态与错误码**：新增稳定结果 `INVITE_EXHAUSTED`、`REQUEST_EXPIRED`；撤销/版本冲突/已接受邀请仍为 `CONFLICT`，容量为 `ROOM_FULL`，链接数量上限为 `QUOTA_EXCEEDED`。列表使用派生 `status` 与 `next_step`，调用方不应自行推断。

- **通知**：新增 `room_invitation_revoked`、`room_join_requested`、`room_join_approved`、`room_join_rejected`；审批相关事件向有权限的管理员或申请人发送 inbox 提示，不向普通成员广播申请正文。

## 问题与限制

1. **设备二维码不在本任务范围**：本任务只提供群邀请二维码，二维码即加入 URL，不是长期身份 token；设备配对二维码由 Q02 单独实现，不能复用本页逻辑。
2. **链接是持有者能力**：任何拿到 `/j/<key>` 的身份都能打开预览；是否成为成员仍由邀请状态、次数、拉黑、移除状态、容量与审批策略决定。需要“仅指定人可加入”时应使用定向邀请，而不是分享链接。
3. **审批附言暂未开放**：`room_join_requests.message` 已预留且默认空串，G02 不开放自定义附言；如需申请人留言应作为后续契约变更统一处理。
4. **状态派生而非全部落库**：`expired`/`exhausted` 在读取时按邀请有效期与次数派生，撤销才是显式持久状态；这保证旧二维码在所有设备得到一致结果，但查询方不能把派生状态当作可写字段。
5. **重复查询实现**：`room-invitations.ts` 与 `room-invite-links.ts` 各有一份邀请视图 `SELECT`，当前语义一致（同样 5 个 viewer 绑定）；后续可抽公共查询，但不影响本任务行为。
6. **邀请窗口限制**：每身份 10 分钟最多 60 次主动邀请（A05 既有规则），批量验收需要拆分身份；这不是 G02 缺陷。
7. **测试环境依赖**：完整 `test:acceptance` 的 presence 用例要求服务端与测试进程使用相同的时间窗参数；参数不一致会表现为 presence 断言失败，与 G02 无关。生产部署使用默认时间窗即可。
8. **状态标记**：任务文件 `当前状态` 仍为 `NOT_STARTED`；本报告由实现者标 `READY_FOR_REVIEW`，需独立验证者在集成 SHA 上复跑并签收后才能标 `VERIFIED`。

## 审查与签收

- 实现过程中修复：邀请失效状态原先统一返回 `CONFLICT`，现按过期/用尽分别返回 `REQUEST_EXPIRED`/`INVITE_EXHAUSTED`；审计表重建后补回丢失的两个索引；撤销邀请时同批收敛 pending 申请；网页 `callTool` 对 `isError` 的检查确保审批/撤销失败不会被当成成功。
- 审查关注点：链接预览是否泄露消息或凭据；确认前是否可能写入成员；审批批准是否在同一事务复核邀请状态、次数、拉黑、移除状态与容量；`used_count` 与成员写入是否原子一致；被移除者是否可能借旧链接或旧定向邀请重入；撤销后旧二维码是否在所有设备一致失败；网页分享区是否只保留内存明文。
- 独立验证需在集成 SHA 上复跑 `typecheck`、`test:protocol`、`test:acceptance`（两端一致的 presence 参数）与 `test:web`，并确认 G02-T01–T04 的原始输出。后续影响邀请、审批、成员代次、容量或通知的改动须重开本报告受影响验收。
