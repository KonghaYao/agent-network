## 最终行为与变更

### 1. 一次性挑战与独立设备凭据

- 已登录设备调用 `network_device_pairing_create` 生成 12 位 Crockford 短码挑战（约 60 bit 熵，显示为 `XXXX-XXXX-XXXX`），默认 5 分钟有效；明文 challenge 只在首次响应出现一次，服务端只保存带域分隔前缀的 SHA-256。同一 `request_id` 重放返回 `TOKEN_NOT_REPLAYABLE`，`operations.result_json` 不含 challenge 或 pair URL。见 `src/domain/device-pairings.ts`。
- 新设备在 `/pair` 用自己生成、尚未注册的 token 调用 `network_device_pairing_join`；服务端把 challenge 绑定到该 token 摘要，返回设备名称、平台与从摘要派生的确认码，不返回 token。已绑定其他 token 的挑战不能被第三台设备抢绑；错误设备证明累计 `attempts`，达到 `max_attempts` 后挑战转为 `cancelled`（reason `attempts_exceeded`）。
- 已登录设备用 `network_device_pairing_list` 查看待确认设备，用 `network_device_pairing_approve` 明确批准，或用 `network_device_pairing_cancel` 拒绝/撤销。批准只写配对状态与安全事件，不创建 credential；新设备随后用 `network_device_pairing_redeem` 兑换同 actor 的独立 credential。未批准、过期、已用、已撤销、超限、设备不匹配分别返回稳定 `PAIRING_INVALID` reason 与下一步文案。
- 新设备 token 由浏览器本地生成并只保存在本地；redeem 响应从不返回 token。已登录设备创建挑战、批准与拒绝都要求当前 actor 的已注册凭据；新设备 join/redeem 要求 token 尚未注册，避免把已登录凭据绑定到另一 actor。
- 兼容选择：`network_device_pairing_create` 要求已登录（契约基线曾把“未登录可调用”列为开放建议）。这样挑战在创建时即绑定 actor，避免匿名挑战被他人接管；批准仍必须由同一 actor 的已登录设备显式完成。

### 2. 设备列表、最后活动与单设备撤销

- `network_device_list` 返回当前 actor 的设备：`device_id`、label、platform、status、created_at、last_seen_at、current、有效/总 credential 数。`current` 按当前 Bearer 的 `credential.device_id` 标记；`last_seen_at` 取 `devices.last_seen_at` 与 credentials 最近活动的较大值。认证路径以 `LIMITS.deviceActivityThrottleMs` 节流写入，不写事件、不产生未读。
- `network_device_revoke` 在同一 `db.batch()` 内：标记 `devices.status='revoked'`、撤销该设备全部有效 credentials、取消该设备创建的待确认配对挑战、写 `device_revoked` inbox 事件与 outbox。不重建 actor、不影响其他设备。
- 安全流收口：`authenticate` 解析出 credential 后，`subscriptions/listen` 把 `credential_id` 传给 `serveActorStream` 与 `NotificationHub.subscribeActor`。撤销成功后对每个被撤销 credential 调用 `NOTIFICATION_HUB.revokeCredential`，立即关闭该设备的活跃 stream；hub 同时记录已撤销 credential，阻止撤销与建立订阅并发时旧凭据迟到注册。其他设备的连接继续接收。测试 T01 验证了被撤销设备 stream 收到 `complete`，另一台设备 stream 保持打开，且被撤销 token 的 `network_me` 返回 HTTP 401 + `CREDENTIAL_INVALID`。
- A01 语义保持：设备撤销只处理 credentials/devices，不改变 actor 管理关系、归档或停用；D04–D08 的 assignment/task/delivery 语义未修改。

### 3. 身份切换、旧方式与本地缓存分区

- 浏览器新增 `src/web/chat-identity-script.ts`：当前 token 仍是 `agent-network-token`；已确认身份按 actor 写入 `agent-network-identity-v1:<actor>`，退出只删除当前身份的记录、Agent 注册表、发送意图、草稿与 sync 游标，其他身份保留并可在退出页显式切回。
- Agent 注册表改为 `agent-network-agents-v1:<owner_actor_id>`；旧全局 `agent-network-agents-v1` 只作为只读兼容回退，退出时只移除当前 owner 的条目。
- 草稿按 `agent-network-draft-v1:<actor>:<room>` 持久化；切房恢复、发送成功清理、退出只清理当前身份。发送队列继续使用 `agent-network-outbox:v1:<actor>`；sync 游标使用 `agent-network-sync-v1:<actor>`。
- `ensureIdentity` 不再在已有 token 失效时自动创建新 token：没有 token 时仍可首次注册；已有 token 返回 `CREDENTIAL_INVALID` 时显示“凭据失效”状态、重新配对入口与旧方式入口，不发起 `network_register`。只有显式“创建新身份并继续”或显式切换才允许注册。
- 旧 `/#t=` 只由早执行脚本捕获到内存并立即清 hash，不再自动写入 token；主脚本显示“旧方式（长期凭据）”确认弹窗，明确展示原身份、目标身份与长期 token 风险，确认前不切换、不覆盖当前身份。取消保留原 token。切换后原身份记录仍在本机注册表，可再次显式切回。
- 配对弹窗默认只生成一次性挑战二维码/短码；旧长期 token 入口收进折叠的“旧方式（长期凭据）”，不再是默认按钮文案。

### 4. 离线补读与去重

- `network_sync` 保留原 scope/cursor 契约，新增：
  - 每条事件返回 `event_id`（当前等于 event_seq），便于客户端按 id/seq 去重；
  - `head_cursor` 返回当前 head 的游标，首次建立本地游标时无需重放全部历史。
- Web 端在 stream ack/重连后调用 `syncCatchUp`：首次用 `head_cursor` 初始化 `inbox` 与当前房间游标；重连时按游标补读，事件按 `event_id/seq` 去重，之后只刷新会话列表、当前房间、任务与文件状态，不重跑历史任务或重复执行外部副作用。游标只在成功读取后向前推进；`reset_required` 清空本地游标并触发完整刷新。
- 凭据失效时 `syncCatchUp` 与 stream 终止路径都显示明确错误与重新配对入口，不自动注册替代身份。
- 专项 T03 覆盖：断线期间两条提及、任务 offer、联系人申请、群策略/公告变化、另一群被移除；重连后 inbox/room 补读包含对应事件，按 seq 去重后不翻倍，最终游标之后无重复，成员移除后 room sync 返回 `NOT_MEMBER`，任务保持 `offered` 直到显式接受，未读可标记恢复。T04 覆盖：同 actor 新设备不重建 actor；撤销一台后另一台可用；失效 token 不能注册替代身份或补读；A/B 消息与未读互不串扰。

### 5. 数据与迁移

`0036_device_pairing_sync.sql`：

- 目的：扩展 `device_pairings` 保存创建设备凭据、目标设备标识、平台、token 摘要、撤销时间/原因；为按 actor 查询与按 token 摘要查找增加索引；新增 `guard_device_stale`（只接受 `x=0`）。
- 权威状态：pairing 状态机在 `device_pairings`；设备状态与活动在 `devices`；实际认证凭据在 `credentials`。挑战与 token 都只保存 SHA-256 摘要。
- 约束/索引：`idx_device_pairings_actor_status(actor_id,status,created_at DESC)`；`idx_device_pairings_device_token(device_token_hash) WHERE device_token_hash IS NOT NULL`。
- 旧数据映射：已有 credentials 没有 devices 行时按 `(actor_id, device_id)` 回填一条设备；设备只要仍有未撤销凭据就保持 `active`，否则 `revoked`。不回填挑战，不把旧长期 token 二维码解释成已批准的配对。迁移不修改已发布迁移。
- 恢复：配对/设备状态可由 `credentials` 与业务表重新推导出设备列表；删除迁移新列或回滚应用不影响旧 token 认证。迁移在启动时由既有 `migrate()` 顺序应用。

## 问题与限制

1. **真实扫码未自动化**：浏览器测试在 `/pair` 上直接带入 `#c=`，没有调用摄像头/真实扫码 API；二维码编码仍由既有 `src/web/qr.ts` 现场生成。人工需在真实手机上验证相机→`/pair` 的链路。
2. **挑战先到先绑**：若攻击者在合法新设备之前拿到挑战并 join，批准界面会显示攻击者的设备名称/平台/确认码；产品要求已登录设备核对后拒绝。服务端不能在没有额外设备公钥/近场证明的情况下区分“谁先扫到”。本实现提供确认码、设备信息、拒绝/撤销与尝试上限，但不会自动信任先到者。
3. **旧长期凭据仅过渡**：`/#t=` 与 `network_recovery_*` 未删除，只在 UI 中折叠并明确警告；它们仍是长期凭据，泄露后必须由已登录设备撤销对应设备。Q02 没有实现长期凭据的自动过期。
4. **设备改名未实现**：任务中标注为可选的 `network_device_rename` 未加入工具面；当前 label 来自创建/配对时的客户端输入。
5. **单设备撤销的进程边界**：hub 只关闭本进程内的 stream；多实例部署不在当前实现范围。数据库撤销保证新请求立即失败，其他实例的已建立连接需由部署层的多实例广播或重连收敛。
6. **同步补读是客户端辅助**：`syncCatchUp` 只补状态与刷新标记，不逐条重放业务动作；真正的权威状态仍通过 `network_task_list`、`network_contacts_list`、`network_room_get`、未读接口读取。这样满足“订阅恢复不重跑历史工作”，但不提供离线操作队列。
7. **浏览器本地身份表保存多个 token**：为支持显式切回，`agent-network-identity-v1:<actor>` 保存 token；这与既有单 token 本地存储同属敏感本机数据，必须依赖站点隔离与本地设备安全。退出只清当前身份，其他身份 token 仍在本机。
8. **配对事件不产生待办**：`device_pairing_requested` 只推进 inbox head/outbox，`pending_count` 不变；未打开配对弹窗的已登录设备需要主动刷新或依赖 stream 的 `device` informational 项。这是安全审批提示，不是 Agent 新工作。
9. **未做真实多设备/多浏览器手工验收**：T01–T04 使用独立 token/连接模拟设备；真实手机与桌面同时在线、网络切换与锁屏场景仍待独立验证。
10. **README/CLAUDE 只做必要对齐**：Q01 将全量核对所有历史计数、稳定不变量与命令；本报告只修改与新行为直接冲突的段落。README 仍可能保留旧的协议/验收计数描述。
