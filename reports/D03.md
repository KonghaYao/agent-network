## 最终行为与变更

### 1. 权威状态与统一投影

- `tasks.status` 是唯一业务状态权威；新增 `src/contracts/task-status.ts` 统一 9 个状态值：`unassigned`、`offered`、`in_progress`、`blocked`、`submitted`、`accepted`、`failed`、`cancelled`、`legacy_completed`，以及文案、说明、阶段（派发/执行/验收/已结束）和 C07 合法迁移表。
- `legacy_completed` 只来自 `0017_task_workflow.sql` 对旧 `room_tasks.done` 的回填；只读展示“历史完成”，`status_hint` 明确说明未经过新验收、不能当作 `accepted`，且 `can_report_progress` / `can_block` / `can_resume` / `can_cancel` 均为假。
- `network_task_get`、`network_task_list` 与网页任务卡片/浮层/我的任务共用同一任务投影：`status_label`、`status_hint`、`phase`、`phase_label`、`progress`；详情额外返回 `progress_history`。`network_task_summary` 仍只返回任务计数，不携带单任务状态文案。前端只在服务端文案缺失时回退到同值静态表，不维护第二套状态表。

### 2. 进度、阻塞与恢复

- 新增 `network_task_progress { request_id, task_id, note?, percent?, assignment_id?, assignment_version?, expected_revision? }`：只有当前负责人且持有当前 active assignment、任务为 `in_progress` 时可写；`note` 与 `percent` 至少一项，`percent` 为 0–100 整数，说明按 UTF-8 最多 `LIMITS.taskProgressNoteBytes`（8 KiB）。写入保持 `in_progress`，只递增 `revision` 并追加审计。
- 新增 `network_task_block { request_id, task_id, reason, ... }`：仅 `in_progress` 可转 `blocked`，`reason` 必填、最多 `LIMITS.taskBlockReasonBytes`（4 KiB），同时写 `tasks.blocked_reason` / `blocked_at`；阻塞不是失败或取消，原负责人保留执行资格。
- 新增 `network_task_resume { request_id, task_id, note?, ... }`：仅 `blocked` 可回 `in_progress`，清空 `blocked_reason` / `blocked_at`，可选恢复说明写入审计。
- `0029_task_progress.sql` 新增只追加的 `task_progress`：`progress_id`、`task_id`、`task_revision`、assignment 标识与版本、actor、前后状态、`percent`、`note`、`blocked_reason`、`created_at`，`(task_id, task_revision)` 唯一。最新进度按 `task_revision` 取一条，历史按 revision 倒序最多 `LIMITS.taskProgressHistoryMax`（20）条；数据库仍保留全部审计行，不保存第二份“当前状态”。
- 所有写入同时校验 owner、当前 active assignment、可选 `assignment_id` / `assignment_version` 与 `expected_revision`（C08）。旧执行版本返回 `ASSIGNMENT_STALE`，revision 过期返回 `VERSION_CONFLICT`，非法状态返回 `CONFLICT` 且 errors details 带权威状态，非负责人返回 `PERMISSION_DENIED` 且带真实负责人。
- 幂等经 `runIdempotent` + 请求载荷 hash：同一 `request_id` 相同载荷返回同一 `progress_id` / revision 且不新增历史或事件；同一 `request_id` 改参数返回 `IDEMPOTENCY_CONFLICT`；同一 revision 并发写只有一个成功，另一个返回 `VERSION_CONFLICT` 或 `ASSIGNMENT_STALE`。

### 3. 事件与通知

- 新增 room scope 事件 `task_progress_reported` / `task_blocked` / `task_resumed`，元数据含 `task_id`、`revision`、`status`、`changed_by`、`assignment_id` / `assignment_version`、`percent`、`has_note` / `note_bytes` 与阻塞原因。
- `src/realtime/stream.ts` 将任务事件映射为 `source='task.updated'`、`kind='task'`、`attention='informational'`，只扇出给 active human；本次事件项新增 `revision`，客户端可按 revision 丢弃乱序提示并补读权威状态。
- 普通进度/阻塞/恢复不创建聊天消息、delivery 或 inbox 待办，不改变 `pending_count`、`inbox_head_seq`、`rooms.head_seq`、未读水位或最后消息；Agent 不收到任务提示。重复与并发写不会重复追加事件。
- D01/D02 的接手、取消、offer 接受/拒绝等控制通知路径未改变；这些路径仍按原房间能力与 delivery/inbox 规则送达责任者。

### 4. 网页与 MCP 展示

- 网页任务卡片显示最新进度摘要（百分比与说明/阻塞原因截断）；详情显示状态说明、阻塞原因、最新进度条与操作者/时间、进度历史，并提供“更新进度”“报告阻塞”“恢复执行”控件。所有写操作携带 assignment 版本与 `expected_revision`；成功后重新调用 `network_task_get` 获取含历史的权威视图，再刷新任务概览、当前房间任务与卡片标记；冲突时显示真实负责人。
- MCP 输出新增 `status_label` / `status_hint` / `phase` / `phase_label` / `progress` / `progress_history?` / `can_report_progress` / `can_block` / `can_resume`；列表只返回最新进度以控制体积，详情才返回历史；写操作结果包含最新进度但不带历史。delivery 的 pending/claimed/completed/failed/cancelled 仍只表示通知处理，任何页面或工具都不把它映射成任务业务状态。

### 5. 工具面、脚本与文档

- 任务工具从 9 个增至 12 个；新增 `network_task_progress`、`network_task_block`、`network_task_resume`，旧任务板工具保持退休；整体工具面 94 个（关闭 Drive 时 85 个）。
- `public/skills/agent_tasks.sh` 新增 `progress` / `block` / `resume` 子命令；`src/mcp/skill.ts` 与 `public/skills/agent-network-skills.md` 说明进度不制造未读、delivery complete 不等于任务完成、`legacy_completed` 不等于 `accepted`，并保持静态/主技能 digest 一致。
- `README.md`、`CLAUDE.md`、`docs/code-index.md` 已同步 D03 语义、文件拆分与验收项。

## 契约、权限与数据变化

- **工具面**：新增 `network_task_progress`、`network_task_block`、`network_task_resume` 及对应输入 schema；任务输出新增 `status_label`、`status_hint`、`phase`、`phase_label`、`progress`、`progress_history?`、`can_report_progress`、`can_block`、`can_resume`；任务流事件项新增 `revision`。均为增量字段，旧客户端忽略后仍可使用原有工具。
- **权限**：进度/阻塞/恢复只允许当前 owner 且持有当前 active assignment；任务状态、`expected_revision`、`assignment_id` / `assignment_version` 在事务闸门中同时校验。`can_*` 只是只读提示，任何旧视图或直接 MCP 调用都会重新鉴权。验收人、非成员、边界外行为沿用 D01/D02。
- **事件/订阅**：新增 room scope `task_progress_reported` / `task_blocked` / `task_resumed`，映射为 human-only informational `task.updated`；不写 inbox、不创建 delivery、不推进 `rooms.head_seq`、不增加未读或 `pending_count`，不唤醒 Agent。事件携带任务 revision，客户端可据此丢弃乱序提示并补读 `task_get` / `task_list`。
- **持久状态**：新增 `task_progress` 追加审计表与唯一索引；`tasks.status` 仍是唯一当前状态，`blocked_reason` / `blocked_at` / `last_progress_at` 复用既有列。未新增第二套状态表，未修改 `0017` 的旧任务映射。
- **限制值**：`LIMITS.taskProgressNoteBytes = 8 KiB`、`LIMITS.taskBlockReasonBytes = 4 KiB`、`LIMITS.taskProgressHistoryMax = 20`，集中在 `src/contracts/limits.ts`。
- **客户端影响**：网页新增进度/阻塞/恢复控件与详情历史；写后重新读取 `network_task_get`，确保展示含历史的权威视图。MCP 客户端可继续只读 `status` / `revision`，但建议使用 `status_label` / `phase_label` 与 `progress` 统一文案。
- **范围边界**：转交提议仍由 D04/D05 的独立对象负责，本任务不实现 transfer；`submitted` 由 D06 提交产生，`accepted` 只能由 D07 指定验收人产生，`failed` 的显式重试/重派仍待后续任务；D03 只保证这些状态不能被进度或 delivery 伪造。

## 问题与限制

1. **全量验收需短 presence 窗口**：服务端与测试进程使用 `AGENT_PRESENCE_ACTIVITY_TTL_MS=5000`、`AGENT_PRESENCE_GRACE_MS=2000`、`AGENT_PRESENCE_SWEEP_MS=1000` 时通过 1634 项。默认窗口下离线发现等待仍可能超过 `scripts/acceptance.ts` 的 30 s 断言，属于既有测试配置限制。
2. **转交未实现**：D03 不创建 transfer 提议、不提前改变任务状态；`task_transfers` 仍未被使用。D04/D05 必须在自己的事务中完成换人、版本递增、旧资格失效与事件，不得复用 `task_progress` 冒充交接。
3. **状态机尚未全部可达**：`submitted` / `accepted` / `failed` 已在契约与迁移表定义，但当前没有 D03 工具产生它们；D06/D07（以及失败/重试任务）接入时必须追加审计并遵守同一 revision/assignment 校验，不能绕过 `task_progress`。
4. **offer 过期仍无清扫器**：D02 记录的过期 offer 不会自动回 `unassigned`，需要取消后重建或后续幂等清扫；D03 未扩大该范围。
5. **任务概览 `done` 计数包含 `legacy_completed`**：沿用 D01 的 `done = accepted + legacy_completed` 统计，详情与卡片文案明确区分“历史完成”和“已验收”；若产品需要单独的 accepted 计数，应另开任务调整 summary 契约。
6. **进度历史只展示最近 20 条**：数据库保留完整审计，MCP 详情和网页最多显示 20 条；列表与写操作结果不返回历史，网页写后通过 `network_task_get` 补读，避免写结果膨胀。
7. **乱序验收边界**：专项覆盖旧 revision/旧 assignment_version 被拒、同 revision 并发单胜出、human stream 收到带 revision 的 informational 提示与幂等重放；未额外构造两个浏览器以不同顺序接收同一批 `task.updated` 的 Playwright 回放，客户端应始终以 `task_get` / `task_list` 的权威 revision 收敛。
8. **后续入口约束**：当前没有任务文件/成果提交入口；D06/D07 接入时每个提交、文件绑定与派生授权入口都必须复用 `activeAssignmentGuard`，不能只在某个 `task_complete` 中校验。
9. **沿用依赖**：`network_task_list` 仍未分页；`task_submissions` / `task_reviews` 未使用；任务附件 GC 已由本轮修复并加入协议门禁；D03 未扩大其余范围。
