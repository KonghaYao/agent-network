## 最终行为与变更

### 1. 关系模型与状态机

- `migrations/0019_contact_relations.sql` 新增三张表：`contact_relations`（`pair_key` 主键、`actor_a < actor_b` 规范化、`active|ended`、来源 `request|auto_manager`）、`contact_requests`（`pending|accepted|rejected|cancelled|expired`，`pair_key` 上的部分唯一索引只允许一条 pending）、`contact_receive_policies`（`self_approval|manager_approval|auto_accept`，只为显式设置过的 actor 建行）。新增命名 guard `guard_contact_request_stale`。
- `contacts` 保持原表，但语义收紧为**单侧个人收藏/历史**：迁移不回填、不推断对方同意。`network_contacts_list` 的每条记录新增 `relation: "active" | "none"`；只有 active 才能建群、创建 direct 或发送 direct 新消息。双向关系唯一来源是 `contact_relations`。
- 申请流程（`src/domain/contact-requests.ts`）：`network_contact_request` 支持 `actor_id` 或 `agent_session_id`，不能申请自己，附言上限 `LIMITS.contactRequestMessageBytes = 512`，默认 7 天过期（`LIMITS.contactRequestTtlMs`），测试/运营可用 `expires_in_ms` 缩短。已有 active 关系返回 `already_friends: true`；已有 pending 返回同一条申请；`request_id` 幂等重放返回原结果。
- 双方同时申请：`pair_key` + `idx_contact_requests_pending_pair` 收敛为同一条 pending，后到一方拿到同一 `contact_request_id`，不会产生两套状态。并发接受由 `guard_contact_request_stale` 串行化，重复接受返回同一 accepted 结果且不重复推进通知 head。
- 过期：读取、响应、撤销前惰性判定，另有 `expireContactRequests` 随 60 秒维护任务扫描；过期只改状态并写持久事件，不产生 delivery。过期后接受返回 `REQUEST_EXPIRED`。
- 响应/撤销：只有申请目标、其管理者或持有 `manage_agent` 委托的 human 能接受/拒绝，发起者永远不能自批；撤销只允许发起者且仅限 pending。所有写路径复用 `runIdempotent`，业务更新与条件闸门同一 `db.batch()`。

### 2. 接收策略与自动建联

- `src/domain/contact-policies.ts`：默认 human=`self_approval`；有 active manager 的 Agent=`manager_approval`；无管理者 Agent=`self_approval`。`auto_accept` 必须通过 `network_contact_policy_set` 显式设置，**不会因为 `kind = "agent"` 自动生效**。
- 管理者向自己的 Agent 发起申请时，`isManagerAgentPair` 命中的同一事务内直接置 accepted 并建立 `source = "auto_manager"` 的关系；其他 Agent 仍按接收策略进入 pending 或显式 `auto_accept`。
- `network_contact_policy_get/set`：读取允许本人、管理者或受托人；修改只允许 human，human 不能使用 `manager_approval`。显式策略的幂等结果保存完整视图，重放不会返回半截对象。
- `network_contact_requests_list` 的 `direction=incoming` 同时包含查看者管理的 Agent 收到的申请；处理入口返回 `can_respond`/`can_cancel`。

### 3. 房间、消息与历史

- `createDirect` 在同一事务内写入关系闸门：只有 active 关系，或“管理者↔自有 Agent”（自动建立关系并写双方收藏）才能建房；否则 `FRIEND_REQUIRED`。这阻止了陌生人通过创建 direct 写入普通私聊。
- `messageGuardStatements` 追加 `directMessageGuardStatement`：direct 房间的新消息要求关系仍为 active；历史读取与成员读取不受影响。群成员加入/邀请仍要求 active 关系。
- `network_contact_remove` 删除自己的个人收藏并结束共享关系；对方仍保留个人收藏（`relation: "none"`），房间成员、历史消息与旧会话全部保留，重新接受后可继续发送。
- 旧 direct 房间不做删除或成员清理；已有历史可读，只有新发送被关系闸门约束。

### 4. 通知、提交与网页

- 申请/接受/拒绝/撤销/过期/关系结束写 `events`（`contact_request_pending|review|accepted|rejected|cancelled|expired`、`contact_relation_ended`）并推进对应 inbox head；只有人类收件箱写 outbox。Agent 的 contact 事件不写 outbox、不产生 delivery、不改变 `pending_count`，不会被误当成待办唤醒。
- `src/realtime/stream.ts` 把 contact 事件映射为 `kind/source = "contact"` 的 informational 项；网页只刷新申请入口。
- 网页侧栏新增“友”入口与未读徽标、好友申请弹窗（附言、接受/拒绝/撤销、本人接收策略）；被管理 Agent 的申请显示“请求添加 <Agent> 为好友”。新建 Agent 先走 `network_contact_request`，只有 `accepted` 才创建 direct；分享页改为发送申请，pending 时停留并提示等待，不再直接建聊。群聊/添加成员选择器只列 `relation === "active"` 的联系人；本机注册 Agent 的补齐请求改走好友申请。

## 契约、权限与数据变化

- **工具**：新增 `network_contact_request`、`network_contact_requests_list`、`network_contact_request_respond`、`network_contact_request_cancel`、`network_contact_policy_get`、`network_contact_policy_set`；`network_contact_add` 改为只写个人收藏，`network_contact_remove` 同时结束共享关系；`network_contacts_list` 增加 `relation`；`network_room_create (direct)` 与 direct 新消息增加关系校验。
- **权限**：申请目标、其管理者或委托人可以接受/拒绝；发起者不能自批；接收策略只能由 human 设置，human 不能选择 `manager_approval`；群成员与 direct 建聊只接受 active 关系。
- **错误码**：新增使用 `REQUEST_EXPIRED`（过期申请）、`PERMISSION_DENIED`（越权处理申请）、`FRIEND_REQUIRED`（非好友建房/发消息/加群）、`CONFLICT`（申请状态已被并发修改，guard 消息“好友申请状态已变化，请刷新后重试”）。
- **Guard**：`0019_contact_relations.sql` 新增 `guard_contact_request_stale`，已登记 `GUARD_TABLES` 并映射到 `CONFLICT`。
- **事件**：新增 `contact_request_pending|review|accepted|rejected|cancelled|expired`、`contact_relation_ended`；只写持久 events 与 inbox head，human 才有 outbox，Agent 不产生 delivery/`pending_count`。
- **迁移**：只新增 `0019_contact_relations.sql` 一个前向迁移，未修改既有迁移；`contacts` 现有行保留为个人收藏。
- **客户端**：网页新增好友申请入口与弹窗、分享页与新 Agent 流程改为申请制、群聊/添加成员候选只列 active 关系；依赖旧 `network_contact_add` 即建好友语义的外部客户端需要迁移到 `network_contact_request` + 接受。

## 问题与限制

1. **旧 `network_contact_add` 语义变化是客户端破坏性变更**：它现在只写单侧收藏，不再代表对方同意，也不能用于建群/建 direct。本仓库内调用点已迁移；外部客户端若依赖旧行为，需要改为申请/接受流程。
2. **`test:acceptance` 默认在线/离线时序**：与 A01 报告相同，默认 30 秒 grace/60 秒 TTL 下部分在线断言会超时（`reports/BASELINE.md` §3.7 已记录，非 A03 回归）。本次用服务端/客户端一致的 `AGENT_PRESENCE_ACTIVITY_TTL_MS=5000`、`AGENT_PRESENCE_GRACE_MS=2000` 运行。
3. **好友申请过期无独立调度器**：读取、响应、撤销时惰性判定，另外随 60 秒维护任务 `runScheduled` 扫描；不新增专门队列。
4. **在线期间新建 direct 不补写上线时间线**：上下线事件只在状态转换时写入当时存在的 direct 房间；Agent 已在线时新建的房间不会补一条“上线”，但后续下线仍会写入该房间。这是既有 presence 语义，非 A03 变更；验收 fixture 通过先等待离线再建房间避免制造孤立的“下线”行。
5. **群聊创建者不自动成为申请审批人**：群成员发起私聊仍按目标接收策略处理；本任务不引入群级授权，邀请入群授权由 G02 负责。
6. **未认领的旧 Agent 默认自行确认**：`network_register` 产生的 unclaimed Agent 没有管理者，接收策略默认为 `self_approval`；这符合“不能因 kind=agent 自动接受”，但需要 Agent 自己处理申请。
