## 最终行为与变更

### 1. 邀请对象与成员关系分离

- `migrations/0023_room_invitations.sql` 新增 `room_invitations`：`kind = direct|link`、`status = pending|accepted|rejected|revoked|expired|exhausted`、目标、邀请人、有效期、`max_uses`/`used_count`、`revision`。G01 只写 `direct`；`token_hash`、`max_uses` 与 `link` 分支预留给 G02，不另建同义表。
- 部分唯一索引 `idx_room_invitations_pending_direct` 保证同一群对同一目标至多一条 pending；目标、房间、token 各有索引。
- 邀请**不是成员**：pending 不写 `room_members`，不计入 `room.member_count`，不占 100 人上限，也不出现在被邀请人的 `network_rooms_list`/`network_room_get` 中。接受时才在同一事务写入 active 成员行。
- 迁移同时建立 `guard_invitation_stale` 与 `guard_invite_targets_missing`；`GUARD_TABLES`、错误映射与迁移同步更新。

### 2. 建群语义

`src/domain/rooms.ts` 的 `roomCreate` 群聊路径改为：

1. 预检所有候选：拉黑优先返回 `BLOCKED`，其次好友关系返回 `FRIEND_REQUIRED`；创建者管理的 Agent 直接 active，其他好友生成 pending 邀请。
2. 任一候选预检不合格时**不创建群**，抛出带 `details.results` 的错误，消息列出全部不合格对象。
3. 创建者写入 `owner` active 成员；自有 Agent 用条件 `INSERT … SELECT` 复核拉黑与管理关系，竞态失败只影响该目标。
4. 其他好友写 pending 定向邀请；预检合格但提交时全部失效时由 `guard_invite_targets_missing` 整批回滚，返回 `FRIEND_REQUIRED`（`details.reason = invite_targets_missing`）。
5. 返回逐对象 `results`（`active|invited|failed` + `code/message`）；失败成员不回滚已成功成员，成功成员不重复添加。
6. 同一 `request_id` 重放读取已存结果中的 `room_id`，收敛为同一群，不重复写成员或邀请。

### 3. 接受与拒绝

`src/domain/room-invitations.ts`：

- `network_room_invite_get` 只返回当前身份的定向邀请，支持 `pending|expired|all` 与分页。
- `network_room_invite_respond` 接受时在同一 `db.batch()` 内复核 pending、目标匹配、有效期、拉黑与容量；并发接受同一邀请由 `guard_invitation_stale` 裁决，后到者返回 `CONFLICT`。成员数已达 100 时返回 `ROOM_FULL`，邀请保持 pending。
- 接受成功写 active 成员、邀请 `accepted`、审计 `member_added`、房间事件 `room_invitation_accepted` 与邀请人 inbox；拒绝写 `rejected` 与 `room_invitation_rejected`。两者都不推进 `rooms.head_seq`，不制造未读。
- owner 退群清空群时，在同一批次撤销该群全部 pending 邀请，避免过期邀请把空群复活成无 owner 的非空群。

## 契约、权限与数据变化

- **迁移**：`0023_room_invitations.sql` 新增 `room_invitations` 与两个 guard 表；`scripts/lib/feedback-unit.ts` 的迁移清单同步到 `0023`。
- **MCP 工具**：新增 2 个；`network_room_create` 群聊结果增加 `results`，房间详情增加 `invited`；`network_room_get`、`network_rooms_list` 的成员计数仍只统计 active。客户端若把 `invited` 当作成员会显示错误，页面与技能正文已明确区分。
- **权限**：只有创建者可提交建群候选；`network_room_invite_get` 只返回当前身份的邀请，目标不匹配返回 `NOT_FOUND`；`network_room_invite_respond` 只允许目标本人操作，接受时重新校验拉黑、有效期与容量。拉黑关系仍优先于好友关系，被拉黑者不能通过邀请路径进入群。
- **通知**：新增 `room_invited`（inbox，`action_required`）、`room_invitation_accepted`/`room_invitation_rejected`（房间 scope）。邀请与接受不增加未读；拒绝不通知被拒绝者之外的成员。
- **限制**：邀请默认不占 100 人容量，接受时原子检查上限；`LIMITS` 是唯一阈值来源。
- **未新增**：独立聊天 REST API、临时表结构补丁、邀请历史表或成员别名列。

## 问题与限制

1. **G01 只实现定向邀请**：开放链接、二维码、审批、撤销、重发与邀请容量预留属于 G02；`token_hash`/`max_uses` 已预留但不启用。
2. **添加成员路径仍是直接加入**：`network_room_members_update` 保持 G03 的 owner/admin 直接添加语义，不生成邀请；本次只改变“建群”路径。若 G02 要求添加成员也走确认，应作为后续任务统一，不在 G01 内改写 G03。
3. **被邀请人网页入口未实现**：被邀请人当前通过 MCP 的 `network_room_invite_get`/`network_room_invite_respond` 处理邀请；创建者网页已展示“等待确认”，但被邀请人网页收件入口尚不存在。
4. **历史可见范围**：接受邀请后能看多少历史由 G07 决定，本次不改变历史分页与可见性。
5. **测试受限**：A05 的 `roomInviteWindowMax = 60`（每身份 10 分钟）限制单身份批量加人，容量用例拆分为 owner 60 次 + 协管 20 次；这不是产品缺陷。
6. **状态标记**：任务文件 `当前状态` 仍为 `NOT_STARTED`；本报告由实现者标 `READY_FOR_REVIEW`，需独立验证者在集成 SHA 上签收后才可标 `VERIFIED`。
