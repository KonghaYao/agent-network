## 最终行为与变更

### 1. 验收工具与授权

- 新增 `network_task_review_accept`：输入 `request_id`、`task_id`、`submission_id`、`version`、非空 `checklist`（每项 `item` / `passed` / 可选 `note`，最多 `LIMITS.taskReviewChecklistMax`）与可选 `expected_revision`。只有当前验收人 `tasks.reviewer_actor_id` 可以调用；非验收人 `PERMISSION_DENIED`，负责人/提交人自验 `PERMISSION_DENIED`。`expected_revision` 与任务当前 revision 不一致返回 `VERSION_CONFLICT`；`version` 不是该 submission 的版本返回 `REVIEW_STALE`；存在 `passed = false` 的项返回 `INVALID_ARGUMENT`，要求改用退回。
- 新增 `network_task_review_return`：同样绑定 `submission_id` + `version`，`reason` 必填且去除首尾空白；只有当前验收人可以退回，负责人/提交人不能自退。任务已离开 `submitted`、版本已处理或 `version` 不匹配统一返回 `REVIEW_STALE`（D06 旧入口仍按兼容语义返回 `CONFLICT`）。
- 新增 `network_task_reviewer_set`：创建者、当前负责人或群管理员可显式指定/替换验收人；终态任务返回 `CONFLICT`，`expected_revision` 不一致返回 `VERSION_CONFLICT`，目标不是 active 成员或已停用返回 `INVALID_ARGUMENT`，目标等于当前负责人或 pending 提交人时 `INVALID_ARGUMENT`。
- 创建任务时默认验收人仍是调用者；创建、提交与验收三个入口都拒绝“执行者验收自己”：创建时负责人与验收人相同直接拒绝，提交时若当前验收人就是提交人返回 `PERMISSION_DENIED`，验收/退回时再次检查提交人与负责人身份。历史数据或竞态无法绕过自验。
- 三个工具在 `src/mcp/tools.ts` 注册为非只读，输出分别复用 `taskSubmissionResultSchema` 与 `taskResultSchema`；任务工具合计 25 个。D06 的 `network_task_submission_return` 保留，避免破坏 D06 客户端与验收，但网页已切换到版本绑定的新入口。

### 2. 验收通过与原子终态

- `taskReviewAccept` 经 `runIdempotent` 在一个 `db.batch()` 内写入：operations、成员 guard、`reviewVersionGuard`、任务 revision guard、`status = 'submitted'` guard、submission pending guard、submission 置 `accepted`、`task_reviews(decision = 'accept', checklist_json = ?)`、任务置 `accepted` + `accepted_at` + `revision + 1`、`task_accepted` room 事件与 `room:<id>` outbox。任一步失败整批回滚，不会出现“清单已写但任务未通过”或空验收。
- `task_reviews.submission_id` 在 0017 中唯一，一个版本只有一条验收结论。重复验收先用 `request_id` 命中 operations 返回原结果；换新 `request_id` 时读取已 `accepted` 的任务与 submission，返回同一 `currentReviewResult` 快照，不追加 review、不重复写事件、不增加 Agent 待办、不推进 `rooms.head_seq`、不产生第二次外部回写。
- 通过与退回并发时由 `reviewVersionGuard`、task revision/state guard 与 submission pending guard 竞争，只有一条事务成功；失败方得到 `REVIEW_STALE`，读取到唯一终态。`accepted` 是终态，之后不能再次进入验收或退回；追加工作必须创建新任务并通过 `parent_task_id` 关联。
- 验收事件是 human-only：`task_accepted` 只映射为 active human 的 `source: 'task.updated'` / `kind: 'task'` informational 流项，不创建 delivery、不增加 `pending_count`、不产生未读。

### 3. 退回与重新交付

- `taskReviewReturn` 与 D06 `taskSubmissionReturn` 共用内部 `returnSubmission`；review 模式在 payload 摘要中加入 `version`，旧入口未传版本时摘要保持不变，保证 D06 既有 request_id 重放不失效。
- 退回在同一事务内写 `task_reviews(decision = 'return', reason, checklist_json = '[]')`、submission 置 `returned`、任务 `revision + 1`。原负责人仍是 active 成员且 actor 未停用时，任务回到 `in_progress`，生成 `assignment_version = max + 1` 的新 active assignment；原负责人失权、退群或停用时任务转 `blocked`，`blocked_reason = 'owner_lost_eligibility'`，清空负责人与 `current_assignment_id`。旧 submission 与旧 assignment 不复活，也不会被新版本覆盖。
- 重新提交只接受退回后创建的新 active assignment，生成 v2；v1 保持 `returned`，`is_current = false`。对 v1 的迟到通过/退回在重交后返回 `REVIEW_STALE`，不能修改 v2 的 pending 结论。
- 退回事件 `task_returned` 同样只写 room scope / outbox，由 stream 投影为 human-only informational；不创建消息、delivery 或 inbox 待办。

### 4. 验收人可用性与改派

- `TaskView` 新增 `reviewer_available`：读取时校验验收人仍是 active 成员且 actor 未停用；`task_list` 批量读取，避免逐任务查询。验收人退群或被停用不会自动验收、也不会自动改派，任务保持 `submitted`（或退回后的 `blocked`），读取侧显示不可用并提示需要改派。
- 退群验收人的迟到通过/退回因不再是房间成员，按统一授权返回 `NOT_FOUND`；仍是成员但已不是验收人时返回 `PERMISSION_DENIED`。两类情况都不会改变任务终态。
- 有权限者通过 `network_task_reviewer_set` 显式替换验收人，写 `task_reviewer_changed` room 事件并 `revision + 1`；改派后任务仍为 `submitted`，新验收人才能通过或退回。网页在 `can_set_reviewer` 时显示成员选择与“改派验收人”按钮，排除当前负责人。

### 5. 终态、追加任务与关系

- `accepted` 终态不可重开；`network_task_create` 新增可选 `parent_task_id` / `related_task_id`。父任务必须与当前房间相同、在当前历史边界内、状态为 `accepted` 或 `cancelled`；关联任务必须同房间可见；两者不能相同。父/关联只表达关系，不复制状态、不授予执行权。
- 默认 `taskCreate` 的行为、校验顺序与既有 `payloadHash` 不变；新字段仅在实际传入时加入摘要，旧任务重放仍命中原结果。`TaskView` 返回两个可空字段，网页详情提供“查看父任务/关联任务”，已验收或已取消任务的详情提供“追加任务”入口，创建弹窗预填 `parent_task_id` 并提示父任务不会被重开。

### 6. 网页、技能与验收脚本

- 新增 `src/web/chat-task-review-script.ts`（低于 1000 行）并拼进 `chatClientScript`：按 `acceptance_criteria` 行生成逐项复选框与备注输入，全部通过才能提交 `network_task_review_accept`；任一未通过时阻止并提示使用退回；详情显示验收人可用性警告、父/关联任务链接；已结束任务提供追加任务入口。
- `src/web/chat-task-submission-script.ts` 的退回入口改用 `network_task_review_return` 并携带当前 `submission_id` + `version`；提交历史显示验收清单逐项结果（✓/✗ 与备注）。`src/web/chat-panels.ts` 新增 `task-review-modal`，`src/web/chat-styles.ts` 增加清单、备注、验收人警告样式；既有 DOM id/class 与任务弹窗行为保持不变。
- `public/skills/agent-network-skills.md` 与 `src/mcp/skill.ts` 同步 D07 生命周期、验收/退回/改派/版本绑定与 `REVIEW_STALE` 文案，保持同一份统一正文与 digest；`scripts/verify-protocol.ts` 更新工具计数 22 → 25，并断言三个新工具、输入/输出 schema、`reviewer_available` / `can_accept_review` / `can_set_reviewer`、`accepted_at`、清单字段与技能正文；`scripts/acceptance.ts` 注册 D07 专项；`scripts/lib/task-review-acceptance.ts` 覆盖 D07-T01..T03。

## 契约、权限与数据变化

- **错误码**：新增 `REVIEW_STALE`，用于旧 submission/version 或已被其他验收结论占用的版本；`VERSION_CONFLICT` 仍只表示读取的 `expected_revision` 已变化，二者不混用。对应闸门表 `guard_review_stale` 只接受 `x = 0`，映射在 `src/storage/transactions/runner.ts`。
- **迁移 `0033_task_review_acceptance.sql`**：给 `tasks` 追加可空 `parent_task_id` / `related_task_id` 与两个读取索引，给 `task_reviews` 追加 `checklist_json TEXT NOT NULL DEFAULT '[]'`，新建 `guard_review_stale`。不重建已发布表，不改写既有行，不删除数据。权威状态仍是 `tasks.status` / `tasks.revision` / `task_submissions.status`；`checklist_json` 只是该条 review 的证据快照，`parent_task_id` / `related_task_id` 只表达关系。旧数据映射：既有任务关系为 `NULL`，既有 review 清单为 `[]`；恢复时旧代码可忽略新增列与闸门表，数据库保持可用。
- **MCP 输出**：`TaskView` 增加 `reviewer_available`、`parent_task_id`、`related_task_id`、`can_accept_review`、`can_set_reviewer`；`TaskSubmissionReviewView` 增加 `checklist`。`can_return` 与 `can_accept_review` 只对“当前验收人 + 非负责人/提交人 + pending 版本 + 任务 `submitted`”为真。`task_list` 批量计算验收人可用性，`task_get` 单独计算。
- **工具契约**：任务工具 22 → 25。`network_task_review_accept` / `network_task_review_return` / `network_task_reviewer_set` 都是写工具，均要求 `request_id` 幂等并校验任务 revision；没有新增只读工具或 REST 入口。D06 `network_task_submission_return` 保留为兼容入口（可选 `version`），网页不再使用。
- **事件与通知**：`task_accepted` / `task_reviewer_changed` 与既有 `task_returned` 只作为 room scope 事件与 `room:<id>` outbox 写入，由 `src/realtime/stream.ts` 投影为 human-only `task.updated`；不创建 delivery、不写 `inbox:{actor}`、不改变 `pending_count`、不推进 `rooms.head_seq`。
- **客户端影响**：网页新增验收清单弹窗、改派验收人、验收人不可用提示、父/关联任务链接与追加任务入口；退回入口改为版本绑定。既有 DOM id/class、任务详情操作顺序与单文件行数限制保持不变。

## 问题与限制

- 按要求未运行全量 `bun run test:acceptance`；D07 专项与协议、网页、类型检查已在本地通过，集成阶段需统一跑全量验收并复验计数。
- 网页只提供“从已验收/已取消任务追加新任务”的 `parent_task_id` 入口；`related_task_id` 已通过 MCP 创建参数与校验支持，但未在网页表单中单独暴露，避免新建任务弹窗继续膨胀。需要网页录入关联任务时可复用同一创建参数。
- 验收人退群/停用不会主动改写任务或发送额外通知；任务保持 `submitted`/`blocked`，由创建者、当前负责人或管理员在下一次读取后显式改派。这是有意的“不自动通过”语义，不是漏写状态。
- 目前没有外部业务回写通道；“重复通过不重复外部回写”由唯一 review 行、唯一 `task_accepted` 事件与幂等 operations 保证；后续接入外部回写时必须复用同一事务结果，不能在事件消费侧再写一份验收结论。
- `accepted` 终态与追加任务关系已实现，但跨设备长历史、任务转交等其余 Q01 范围未在本任务展开。
