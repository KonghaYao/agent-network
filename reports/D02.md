## 最终行为与变更

### 1. 接受（accept）

- `network_task_accept { request_id, task_id, assignment_id?, expected_revision? }` 只允许当前 `offered` assignment 的候选负责人（human 或 Agent）调用；验收人、非候选人、非房间有效成员均被拒绝。
- 服务端先按 `assignment_id`、assignment 状态与 `tasks.revision` 预检，再在 `runIdempotent` 事务中执行 `guard_task_state`、`guard_version_conflict`、`guard_assignment_stale`、`guard_request_expired` 与成员/拉黑闸门；迟到请求不会覆盖更新的指派。
- 接受原子完成：`tasks.status → in_progress`、`owner_actor_id = caller`、`revision + 1`、assignment `offered → active` 并写 `accepted_at`，同时写 room scope `task_offer_accepted` 事件与 `room:<id>` outbox。只产生一个当前 owner；同一人两设备并发接受只有一个成功。
- 接受不调用 delivery 完成路径：关联 delivery 的 pending/claimed 状态、`attempt`、`claim_id` 不因接单而改变；任务也不会进入 `accepted` 终态。

### 2. 拒绝（decline）

- `network_task_decline { request_id, task_id, assignment_id?, expected_revision?, reason? }` 同样只允许当前 offer 的候选负责人调用；`reason` 可选，最长 `LIMITS.taskCancelReasonBytes`，只进入事件审计，不复制到消息。
- 拒绝原子完成：任务回 `unassigned`、清空 `owner_actor_id` 与 `current_assignment_id`、`revision + 1`；assignment `offered → declined` 并写 `ended_at`。
- 同一事务内取消该 assignment 仍为 pending/claimed 的 offer delivery，按 pending 行数原子递减 recipient `pending_count`，写 `delivery_cancelled` inbox 事件与 inbox head，但不向 recipient 自己写 `inbox:{actor}` outbox，避免拒绝者被自己的状态变更再次唤醒。
- 默认不自动尝试全群其他成员、不生成新 assignment；重新指派必须由有权限者显式调用 `network_task_offer`，并产生新的 `assignment_version`。

### 3. 版本分层与冲突快照

- `network_task_accept` / `network_task_decline` / `network_task_claim` / `network_task_cancel` 均支持可选 `expected_revision`，在事务内以 `tasks.revision` 做 CAS；`network_task_offer` 继续使用读取时的 `expected_revision`。
- 冲突分类：旧 offer / 已被接受 / 已被替换的 assignment 返回 `ASSIGNMENT_STALE`；公开领取竞争返回 `CLAIM_CONFLICT`；任务仍待领取但 revision 已变化返回 `VERSION_CONFLICT`；offer 过期返回 `REQUEST_EXPIRED`。
- `ASSIGNMENT_STALE`、`CLAIM_CONFLICT`、`CONFLICT`、`VERSION_CONFLICT`、`REQUEST_EXPIRED` 的错误 `details` 统一附带权威快照：`task_id`、`status`、`revision`、`owner_actor_id`、`owner_name`、`assignment_id`、`assignment_version`、`assignment_status`。失败方无需猜测“谁赢了”。
- 公开领取时，如果任务已被他人领取（`in_progress` 且有 owner），即使请求携带的 revision 也已过期，优先归类为 `CLAIM_CONFLICT`；只有任务仍待领取但 revision 变化时才返回 `VERSION_CONFLICT`。

### 4. 事件与读取视图

- 房间任务事件新增 `task_offer_accepted` / `task_offer_declined`，继续映射为 `source='task.updated'`、`kind='task'`、`informational`，只扇出给 active human；不写 inbox、不推进 `rooms.head_seq`、不产生未读。
- `network_task_get` / `network_task_list` 的 `can_accept` / `can_decline` 只对当前候选且 offer 未过期时为真；`can_claim` 仍只对 `unassigned` 且非验收人的有效成员为真。它们只是 UI 提示，服务端在每次写入时重新校验资格、版本与有效期。
- 网页任务详情新增“接受任务”和“拒绝任务”（含可选原因）入口，请求携带 `assignment_id` 与当前 `revision`；领取/取消也改为携带 `expected_revision`。冲突后页面重新调用 `network_task_get`，重绘详情并显示“当前负责人：X”，不轮询。

### 5. 工具面、脚本与文档

- 任务工具从 7 个增至 9 个：新增 `network_task_accept`、`network_task_decline`；旧任务板工具保持退休。
- `public/skills/agent_tasks.sh` 新增 `accept` / `decline` 子命令，`claim` / `cancel` 支持 `--expected-revision`；技能正文说明“delivery claim/complete 不等于接受或验收”。

## 契约、权限与数据变化

- **工具面**：新增 `network_task_accept`、`network_task_decline` 及 schema；`network_task_claim`、`network_task_cancel` 增加可选 `expected_revision`。客户端需处理 `ASSIGNMENT_STALE`、`CLAIM_CONFLICT`、`VERSION_CONFLICT`、`REQUEST_EXPIRED` 与 `details` 中的权威 owner；旧客户端不传 `expected_revision` 仍可工作，但失去 CAS 保护。
- **权限**：继续要求 active 成员与历史边界；接受/拒绝额外要求调用者就是当前 assignment 的 `owner_actor_id` 且 assignment 仍为 `offered`；验收人不能接受或领取自己验收的任务；`contact_blocks` 在 accept/claim 路径继续生效。任务身份不带来额外房间权限。
- **事件/订阅**：新增 room scope `task_offer_accepted` / `task_offer_declined`，映射为 informational `task.updated`，只发给 active human；不写 inbox、不推进 head、不产生未读。拒绝仍会取消候选人的 offer delivery 并递减 `pending_count`，对此写 `delivery_cancelled` inbox 事件。
- **持久状态**：无迁移、无新表、无列修改；复用 `tasks`、`task_assignments`、`task_deliveries` 与既有 events/outbox。拒绝把 assignment 置为 `declined` 并结束；接受把 assignment 置为 `active`。`task_transfers`/`task_submissions`/`task_reviews` 仍未使用。
- **网页**：仅在任务详情增加接受/拒绝控件与冲突刷新；不新增接口、不改变消息/文件/监控契约。接受/拒绝按钮由 `can_accept`/`can_decline` 服务端视图驱动，页面不自行推断资格。

## 问题与限制

1. **全量验收需短 presence 窗口**：服务端与测试进程使用 `AGENT_PRESENCE_ACTIVITY_TTL_MS=5000`、`AGENT_PRESENCE_GRACE_MS=2000`、`AGENT_PRESENCE_SWEEP_MS=1000` 时通过 1634 项。默认窗口下离线发现等待仍可能超过 `scripts/acceptance.ts` 的 30 s 断言，属于既有测试配置限制，不是 D02 回归。
2. **offer 过期没有清扫器**：`C07` 规定 `offered` 过期应回 `unassigned`。当前只在 accept/decline 时以 `REQUEST_EXPIRED` 拒绝，并在视图中隐藏接受/拒绝按钮；任务仍停留在 `offered`，而 `network_task_offer` 只接受 `unassigned`，因此过期 offer 需要先取消（终态）或新建任务才能重新派发。建议在 D03 或后续任务中增加幂等的过期转换/清扫，并补对应验收。
3. **网页冲突刷新只覆盖领取路径**：接受/拒绝成功路径与领取冲突路径有浏览器断言；接受/拒绝冲突后的刷新复用同一段 catch，但未单独构造 UI 并发场景。服务端错误快照与专项验收已覆盖。
4. **沿用 D01 的剩余依赖**：成果提交仍校验旧 `room_tasks`（D07/D08）；`task_transfers`/`task_submissions`/`task_reviews` 未使用；`network_task_list` 仍未分页。任务附件 GC 已由本轮修复并加入协议门禁；D02 未扩大其余范围。
5. **能力提示不是授权**：`can_accept`/`can_decline`/`can_claim` 仅为只读提示；任何旧视图、直接 MCP 调用或伪造页面状态都不能绕过服务端事务内的成员、版本、assignment 与有效期校验。
